# 2.3.7.6 - Storage Benchmark and Database Decision Gate

## Objective

Decide whether SQLite + Chroma remains appropriate after the Phase 2.3 source
overhaul using repeatable measurements, not database novelty. Avoid either
premature replacement or indefinite attachment to a store that misses the new
scale and filter requirements.

## Default decision

Keep the current dual-store architecture through the first benchmark:

- SQLite owns canonical identities, facts, coverage, provenance, freshness,
  cursors, and the FTS5 lexical index from 2.3.7.5;
- Chroma owns dense vectors and narrative chunks;
- `Store` remains the public persistence contract;
- the corpus ledger and stable chunk ids reconcile both stores.

The expected 600-security/100,000-item Phase 2.3 scale alone is not sufficient
reason to introduce another database, service, migration, and operating model.

## Step 1: Build a reproducible offline corpus benchmark

Generate or reuse deterministic, non-secret fixtures at:

- 100,000 chunks as the Phase 2.3 hard gate;
- an optional 500,000-chunk forecast run when the measured source growth model
  indicates that scale is plausible before the next architecture review.

Use precomputed deterministic embeddings so the benchmark measures storage and
retrieval rather than model or network latency. Record corpus digest, schema,
hardware, SQLite/Chroma versions, configuration, process state, and whether each
run is cold or warm.

Workloads must include:

- dense, lexical, and hybrid top-k retrieval;
- ticker/source/item-type/date and compound filters;
- authoritative inventory/count queries;
- incremental insert, update, delete, and same-count family replacement;
- restart/open time and first query;
- reconciliation after an interrupted cross-store mutation;
- the supported local concurrency pattern: bounded readers and one writer.

## Step 2: Measure quality and operational cost

Capture:

```text
Recall@k and nDCG@10
p50, p95, and worst bounded latency
index build and incremental mutation throughput
startup/first-query time
peak and steady process RSS
SQLite, FTS, and Chroma disk size
stale/missing/orphan/duplicate identity counts
failure recovery and repair time
```

Use the same query set, filters, embeddings, and scoring code for every candidate.
Do not compare vendor examples or separately tuned toy datasets.

## Step 3: Apply hard keep/replace gates

Keep SQLite + Chroma when the 100,000-chunk run meets all of these:

- lexical p95 below 100 ms;
- dense p95 below 200 ms;
- hybrid p95 below 250 ms before generation;
- filtered hybrid p95 below 300 ms;
- authoritative inventory/count p95 below 50 ms;
- restart/open plus readiness below 10 seconds without full Python corpus load;
- zero unrepaired identity drift after the interruption scenario;
- quality within 0.02 nDCG@10 of the selected baseline;
- daily incremental mutation volume completes comfortably within its refresh
  window on the reference machine.

A replacement investigation is justified only if a hard gate still fails after
one measured, bounded optimization pass, or a newly approved requirement cannot
be supported safely (for example multi-host service deployment or materially
higher writer concurrency). Failure must be attributed to the store rather than
generation, ingestion network time, or an avoidable query implementation.

## Step 4: Time-box replacement pilots only when triggered

Do not build three production adapters speculatively. If the gate triggers,
pilot at most these candidates behind the existing Store/retrieval contracts:

1. [LanceDB hybrid search](https://docs.lancedb.com/search/hybrid-search) for an
   embedded, local-first replacement that combines vector search and full-text
   search in one store.
2. [Qdrant hybrid search](https://qdrant.tech/documentation/search/hybrid-search/)
   when a separately operated service, advanced payload indexes, or greater
   concurrency is an accepted requirement.

SQLite remains the canonical structured/operational database unless a separate
structured-store decision proves otherwise. A vector-store pilot must not absorb
security identity, scheduler cursors, or transaction-oriented facts merely to
claim a single database.

The candidate must match current quality and correctness, materially improve the
failed gate, preserve metadata filters and stable ids, support backup/repair,
remain operable for a local deployment, and have an acceptable migration and
rollback path.

## Step 5: Record the decision without pre-writing the result

After measurements, create `STORAGE-BENCHMARK-RESULTS.md` containing raw summary
tables, the selected decision, rejected alternatives, known limits, and the next
review trigger. Do not create a placeholder results file.

If replacement wins, implementation is a separately approved migration phase
with dual-read comparison and rollback. Phase 2.3.7 does not silently turn a
benchmark into a database rewrite.

## Verification Checklist

- [ ] The current optimized architecture is measured before alternatives
- [ ] Benchmarks use identical corpus, vectors, filters, and quality labels
- [ ] Storage latency is separated from model and ingestion latency
- [ ] Keep/replace thresholds and reference hardware are recorded
- [ ] Replacement pilots occur only after a failed gate or new requirement
- [ ] Any production migration requires a separate approval and rollback plan
