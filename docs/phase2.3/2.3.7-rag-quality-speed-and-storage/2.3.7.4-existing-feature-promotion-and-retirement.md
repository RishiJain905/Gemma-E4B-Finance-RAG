# 2.3.7.4 — Existing Feature Promotion and Retirement

## Objective

Give every implemented but disabled or partially wired RAG capability an explicit
disposition: promote, retain temporarily with an owner and expiry, or remove
completely. Eliminate indefinite dark features, duplicate paths, stale
configuration, and dependencies that exist only for rejected capabilities.

## Step 1: Build a feature inventory

Generate one reviewed manifest from configuration, code, tests, and documentation.
At minimum audit:

| Capability | Current default | Required comparison |
|---|---:|---|
| conversation rewrite | off | single/multi-turn accuracy and latency |
| LLM rewrite fallback | off | incremental gain versus extra model call |
| adaptive RAG | off | correctness, recall, simple-query latency |
| planning call | off | complex-only gain and drift rate |
| deterministic routing | off | routing precision and write avoidance |
| deterministic answers | off | correctness and end-to-end speed |
| evidence sufficiency | off | abstention/coverage accuracy |
| corrective retry | off | recovery versus unnecessary retry rate |
| hierarchical retrieval | off | long-document recall/context precision |
| cross-encoder/LLM reranker | off | nDCG/Recall versus latency/memory |
| retrieval cache | off | hit rate, invalidation, memory, latency |
| llama prompt reuse | off | TTFT/reused-token evidence and compatibility |
| tool-final streaming | off | stream correctness and perceived latency |
| progress events | off | compatibility and overhead |
| graph observer | off | operational value and bounded overhead |

Record the owning code/config/docs/tests and any exclusive dependency for each.

## Step 2: Run controlled promotion arms

Start from a real live Phase 2.2/2.3 baseline. Change one capability group per
arm; do not enable every flag at once.

Recommended order:

1. deterministic routing plus the 2.3.7.3 answer fast path;
2. conversation rewrite and adaptive orchestration;
3. evidence sufficiency, corrective retry, and answer enforcement;
4. hierarchical retrieval after the filing corpus backfill;
5. reranking after the persistent lexical baseline from 2.3.7.5;
6. retrieval cache and prompt reuse;
7. tool-aware streaming/progress and graph observer.

Every arm records quality, eligible-case denominators, p50/p95/TTFT, model calls,
retrieval rounds, prompt tokens, memory, and failure behavior.

## Step 3: Assign one disposition

### Promote

The capability passes its quality, latency, safety, and compatibility gates. Turn
it on in the appropriate default profile and document rollback.

### Retain temporarily

Use only when a named pending prerequisite prevents a fair decision. Record:

- reason and owner;
- exact prerequisite/evaluation;
- expiry milestone (no later than Phase 2.3 sign-off);
- current default and rollback behavior.

### Remove

Delete the feature branch, config/env keys, documentation, exclusive tests,
exclusive dependencies, and dead compatibility code together. Preserve shared
primitives that are still used. Do not leave a permanently false flag around a
rejected implementation.

## Step 4: Simplify configuration profiles

Define documented profiles rather than asking users to coordinate many flags:

```text
legacy          Phase 2.2-compatible rollback
recommended     promoted safe defaults
evaluation      extra trace/evaluation metadata, not production defaults
```

Environment overrides remain possible, but invalid combinations fail validation
or are clamped with an explicit warning. Examples: deterministic answers require
deterministic routing/adaptive orchestration; corrective retry requires evidence
sufficiency; hierarchical retrieval requires indexed section metadata.

## Step 5: Enforce configuration/documentation parity

Extend documentation tests so every feature flag is:

- read by code;
- documented with default and env name;
- assigned to a profile or explicitly internal;
- covered by at least one on/off behavior test;
- absent everywhere after removal.

Track package imports during offline tests so an unpromoted optional reranker does
not force model downloads or heavy initialization.

## Testing

- Load each profile and assert the exact validated effective configuration.
- Reject or warn on invalid flag combinations.
- Compare every promotion arm against the same corpus/model/baseline digest.
- Verify removed keys, imports, docs, and dependencies have no remaining
  references.
- Prove the legacy profile preserves the rollback path.
- Prove recommended-profile startup does not initialize unused heavy models.

## Verification Checklist

- [ ] Every dormant feature has one reviewed disposition
- [ ] Promotion comparisons isolate one capability group at a time
- [ ] Temporary retention includes an owner, prerequisite, and Phase 2.3 expiry
- [ ] Removed features leave no stale flags, docs, tests, or exclusive dependency
- [ ] Recommended and legacy profiles are explicit and validated
- [ ] No optional heavy model initializes unless its promoted feature requires it
