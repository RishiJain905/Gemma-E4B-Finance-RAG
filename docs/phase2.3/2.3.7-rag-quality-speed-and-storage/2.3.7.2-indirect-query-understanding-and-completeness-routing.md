# 2.3.7.2 — Indirect Query Understanding and Completeness-Aware Routing

## Objective

Recognize verbose, indirect, capability-oriented, and compound finance questions
without requiring the user to phrase them as a short ticker command. Route each
request according to its obligations and never treat a partial tool result or
retrieval page as a complete answer.

This task builds on the Phase 2.2 query compiler and adaptive router. It does not
introduce an open-ended agent loop.

## Step 1: Add capability and inventory intent signals

Extend parsing/query-plan vocabulary with stable intent and obligation concepts:

```text
capability_inventory
coverage_check
source_inventory
metric_inventory
corpus_summary
```

Recognize paraphrases such as `know about`, `have data for`, `cover`, `track`,
`available companies`, `supported tickers`, `what can you answer`, and `what is
in your database`. Avoid bare keyword routing: the compiler must distinguish
"What do you know about Apple?" (research request) from "Which companies do you
know about?" (inventory request).

Rule-based compilation runs first. The existing single bounded rewrite/planner
call remains optional only when deterministic parsing cannot resolve the request.

## Step 2: Represent answer obligations explicitly

Add plan obligations for:

- requested entity set or universe scope;
- requested operation and metric/item/source dimensions;
- completeness requirement (`all`, count, top/bottom N, existence, sample);
- requested date/as-of scope;
- qualitative explanation requirement;
- required evidence modes: catalog, structured facts, narrative documents, or a
  mixture.

An `all` request cannot be satisfied by top-k retrieval. A `count` request cannot
be inferred from the number of prompt items. A coverage check cannot be satisfied
by the absence of a semantic hit.

## Step 3: Route metadata questions before general retrieval

Add a deterministic catalog lane before fast/standard/complex RAG lanes:

```text
raw question
  -> bounded compiler
  -> catalog/capability obligations? -> describe_coverage
  -> exact structured obligations?   -> deterministic read tools
  -> otherwise                       -> existing adaptive retrieval lanes
```

Compound requests may combine lanes. For example, "Which semiconductor companies
do you cover, and compare their latest margins?" first resolves the complete
security set from the catalog, then executes bounded structured comparisons. It
must not expand into hundreds of tool calls: plan caps, result limits, and a
transparent request-to-narrow response remain valid.

## Step 4: Make completeness part of route success

A deterministic route is complete only when every plan obligation is covered and
every result used as a complete set says `complete=true`. Add stable incomplete
reason codes:

```text
partial_catalog_page
missing_coverage_dimension
unresolved_universe_scope
missing_metric_coverage
qualitative_evidence_required
result_set_too_large
```

Incomplete routes may contribute evidence, but they cannot trigger the
deterministic final-answer fast path from 2.3.7.3.

## Step 5: Expand the indirect-query golden set

Add concise and verbose paraphrase pairs with the same expected plan and answer
obligations. Include:

- system/corpus inventory;
- one-security coverage checks;
- broad/deep/source-specific coverage;
- indirect comparisons and rankings;
- mixed metadata plus finance questions;
- negative/ambiguous cases;
- conversation follow-ups such as "Which of those also have transcripts?".

Record plan/router accuracy, obligation coverage, set completeness, unnecessary
planner calls, and model-call count.

## Failure behavior

- Ambiguous inventory scope: ask for a narrow clarification or return a labeled
  summary; do not guess a universe.
- Result set exceeds execution caps: disclose the size and offer filters rather
  than silently sampling.
- Planner/rewrite failure: keep the deterministic plan and existing fail-soft
  legacy route.
- Catalog unavailable: return the structured unavailable result from 2.3.7.1.

## Testing

- Map concise and verbose paraphrases to identical normalized obligations.
- Distinguish company research from system-inventory wording.
- Prove `all` and `count` cannot be satisfied by a top-k retrieval sample.
- Prove catalog questions route without embeddings or model calls.
- Exercise mixed catalog plus structured-fact requests under execution caps.
- Carry a prior inventory result into a bounded follow-up without cross-session
  leakage.
- Fault the optional planner and prove deterministic fallback remains truthful.

## Verification Checklist

- [ ] Indirect and verbose questions compile to explicit obligations
- [ ] Capability/catalog intents are distinct from ordinary company research
- [ ] Completeness requirements participate in route success
- [ ] Top-k retrieval is never presented as an exhaustive inventory
- [ ] Catalog questions avoid model and embedding calls
- [ ] Existing adaptive caps and fail-soft behavior remain intact
