# 2.3.7.7 - Quality, Latency Evaluation, and Rollout

## Objective

Prove that the Phase 2.3.7 changes improve indirect-query correctness,
completeness, retrieval efficiency, and end-to-end speed without weakening
grounding or existing finance behavior. This is the promotion gate for 2.3.7 and
an input to the final Phase 2.3 sign-off in 2.3.6.2.

## Step 1: Establish real baselines

Before changing defaults, capture the current implementation with the same
corpus snapshot, model build, prompts, hardware, and golden-set digest. Replace
placeholder or empty baseline fields with measured values and record unavailable
metrics as unavailable rather than zero.

Separate the following timings:

```text
intent/plan
catalog or structured tools
dense retrieval
lexical retrieval
fusion/reranking
prompt construction
model time-to-first-token and total generation
end-to-end
```

This prevents generation latency from hiding retrieval regressions and prevents
fast retrieval from being mistaken for a fast user response.

## Step 2: Expand the labeled evaluation sets

Add versioned offline cases for:

- exact, paraphrased, verbose, and conversational capability inventory;
- complete ticker/source/type/metric lists and counts;
- one-security coverage checks and negative cases;
- indirect fact, comparison, ranking, and calculation questions;
- qualitative questions that must retain model generation;
- temporal/as-of, former membership, freshness, and source-conflict cases;
- aliases, ticker changes, unresolved entities, and intentionally unsupported
  requests;
- lexical exact-match, phrase, filing-form, event, and semantic queries;
- repeated queries for cache/revision behavior;
- partial pages and result sets that must never be called complete.

Each case labels expected obligations, eligible route, required completeness,
evidence ids or structured values, whether generation may be skipped, and any
acceptable refusal/clarification.

## Step 3: Score correctness and efficiency

Report at least:

- intent/plan accuracy and obligation coverage;
- inventory set precision, recall, exact count, and invented-item count;
- structured value/unit/period accuracy;
- citation/evidence resolution and numeric support;
- Recall@k and nDCG@10 by query family and source category;
- deterministic fast-path eligibility precision and recall;
- model, embedding, planner, retrieval-round, and tool-call counts;
- p50/p95 stage, TTFT, and end-to-end latency;
- cache hit/miss/invalidation and prompt-reuse metrics where promoted;
- peak RSS and startup readiness for lexical/storage changes.

Aggregate scores must include denominators and per-family results. A strong
direct-query average cannot hide failed inventory or indirect-query classes.

## Step 4: Enforce promotion gates

- Explicit all-ticker inventory has set precision/recall 1.0, exact count, and
  zero invented tickers against the canonical active registry.
- Capability query routing precision is at least 0.98.
- Indirect/verbose query exact-plan accuracy improves by at least 15 percentage
  points over baseline on the dedicated set, without lowering direct-query
  accuracy by more than 1 point.
- Eligible deterministic answers make zero model calls and are at least 90%
  faster end-to-end than their model-generated baseline.
- Ineligible, partial, conflicting, or qualitative cases never skip generation
  solely for speed.
- Existing retrieval nDCG@10 regresses by no more than 0.02; new lexical families
  meet their labeled Recall@10 targets.
- Non-fast-path end-to-end p95 regresses by no more than 10% unless a documented
  quality gain is explicitly accepted.
- Persistent lexical and storage gates from 2.3.7.5 and 2.3.7.6 pass.
- Every evaluated dormant feature receives the disposition required by 2.3.7.4.

## Step 5: Roll out by profile

1. Run the new catalog/coverage path in shadow mode and compare sets.
2. Enable deterministic routing with generation still required.
3. Enable the deterministic answer fast path for inventory only.
4. Expand the allowlist one typed answer class at a time.
5. Promote FTS5 hybrid retrieval after shadow quality/latency comparison.
6. Enable only the other features marked `Promote` in the recommended profile.

At every step retain the legacy profile, record rollback criteria, and compare a
fixed canary set. Roll back the affected capability rather than all ingestion.

## Step 6: Integrate with Phase 2.3 sign-off

2.3.6.2 remains the phase-wide source, graph, migration, and ingestion sign-off.
It may complete only after this spec records:

- the final recommended/legacy profile diff;
- complete feature dispositions;
- coverage and indirect-query results;
- retrieval/storage benchmark results;
- deterministic-answer correctness and latency results;
- unresolved limits and an explicit ship/rollback decision.

Create `RESULTS.md` in this folder only after implementation and measurement.

## Testing and verification

- Keep all default evaluation and gate tests deterministic and offline-safe.
- Mock model, embedding, planner, and Store calls when asserting call counts.
- Use a seeded corpus and precomputed embeddings for latency/storage harnesses;
  live model/provider measurements are separate opt-in evidence.
- During implementation, run scoped gates while iterating. The final repository
  exit command remains:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\verify.ps1
```

The expected terminal line is `VERIFY: PASS`.

## Verification Checklist

- [ ] Baselines are measured against a fixed corpus/model/config digest
- [ ] Inventory and indirect-query families have separate reported metrics
- [ ] Accuracy, completeness, grounding, calls, and latency are all gated
- [ ] Generation is skipped only for proven-complete typed answers
- [ ] Rollout is staged and the legacy profile remains a tested rollback
- [ ] Phase 2.3 cannot sign off before 2.3.7 results and dispositions are complete
