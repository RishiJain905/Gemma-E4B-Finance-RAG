# 2.3.7.5 - Persistent Lexical Index and Hybrid Retrieval

## Objective

Replace full-corpus, process-local BM25 materialization with a persistent,
incrementally maintained lexical index. Preserve the existing dense retrieval,
RRF fusion, optional reranking, Store facade, and fail-soft query behavior.

The current lexical index is acceptable for a small corpus, but rebuilding it
from every Chroma document increases startup time and memory with corpus size.
Refreshing only when the document count changes can also miss a replacement that
deletes and adds the same number of chunks.

## Decision

Use [SQLite FTS5](https://www.sqlite.org/fts5.html) as the default lexical index.
It is already inside the structured store boundary, supports BM25 ranking, adds
no service or large dependency, and can update in the same transaction as the
Phase 2.3 corpus ledger.

Use a normal content-bearing FTS5 table initially so deletes and updates are
portable across supported SQLite runtimes. A contentless-delete variant may be
evaluated later only when runtime support and measured storage savings justify
the added migration branch.

## Step 1: Add a persistent chunk index

Add an additive migration for:

```text
corpus_fts: title, body, ticker, source_category, item_type, chunk_id UNINDEXED
lexical_index_state: schema_version, indexed_revision, indexed_at, row_count
```

Each `chunk_id` is the same stable identifier recorded by the normalized corpus
ledger and used in Chroma. Do not derive lexical identity from insertion order or
Python `hash()`.

At setup/migration time, probe FTS5 support explicitly. If it is unavailable,
startup remains successful, reports `lexical_mode="degraded"`, and uses the
existing bounded vector-only or legacy lexical fallback selected by config.

## Step 2: Maintain the index incrementally

Every committed corpus-family mutation carries its lexical delta:

- insert new chunks;
- replace changed chunks by stable id;
- delete retired family chunks;
- retain unchanged chunks without rewriting them;
- advance `indexed_revision` only after the full SQLite transaction commits.

The same-count replacement case must change the revision and lexical rows. Index
freshness is revision-based, never count-based.

Add a bounded rebuild/repair command that streams normalized chunks in batches,
records progress, can resume safely, and never calls an embedding or generation
model. A reconciliation mode reports and repairs missing, duplicate, stale, or
orphan lexical rows against the corpus ledger.

## Step 3: Query FTS5 without materializing the corpus

The lexical stage:

1. compiles a bounded FTS query from normalized user terms;
2. applies security, source, item type, and date predicates through indexed
   corpus metadata;
3. ranks candidates with FTS5 `bm25()`;
4. returns stable chunk ids and normalized scores;
5. hydrates only the selected chunks from Chroma/Store;
6. feeds the existing RRF fusion and optional reranker contracts.

Escape or reject invalid FTS syntax rather than concatenating raw query text.
Keep result limits hard-bounded. An FTS error fails soft to dense retrieval and
records the degraded stage in timings/trace metadata.

## Step 4: Keep retrieval revision-consistent

Retrieval captures one corpus revision. If the SQLite lexical revision and
Chroma-visible revision do not match, it may use the last consistent revision or
skip lexical fusion for that request; it must not silently fuse two generations
of the corpus.

Cache keys include the corpus revision, normalized filters, retrieval profile,
and candidate limits. Mutation invalidation remains revision-based.

## Migration and rollout

1. Create the FTS schema with lexical retrieval disabled.
2. Backfill in bounded batches from the normalized corpus/chunk records.
3. Reconcile ledger, FTS, and Chroma identities.
4. Shadow-query the old and new lexical implementations.
5. Promote FTS5 only after the quality and latency gates pass.
6. Remove `rank_bm25` and the full-corpus loader only after rollback coverage is
   provided by a release/profile boundary.

No re-embedding is required for the lexical migration.

## Acceptance gates

At the seeded Phase 2.3 scale of at least 100,000 chunks on the documented
reference machine:

- warm lexical search p95 is below 100 ms;
- warm hybrid retrieval p95 is below 250 ms before model generation;
- startup does not load all document text into Python memory;
- same-count replacements are visible on the next revision;
- reconciliation reports zero duplicate, stale, missing, or orphan lexical ids;
- retrieval nDCG@10 regresses by no more than 0.02 from the best Phase 2.2/2.3
  baseline;
- a lexical failure still returns a bounded dense result.

Record cold and warm timings, process RSS, index size, build rate, incremental
update rate, and quality metrics; do not report only the fastest run.

## Testing

- Build a deterministic offline fixture with inserts, updates, family deletes,
  same-count replacements, and restart persistence.
- Compare lexical rankings with labeled exact-symbol, phrase, form, and finance
  terminology queries.
- Verify filters apply before candidate truncation.
- Inject invalid syntax, unavailable FTS5, stale revision, and corrupt index
  states; assert bounded fail-soft behavior.
- Assert rebuild batches remain idempotent and resumable.
- Assert the query path never scans or materializes all Chroma documents.

## Verification Checklist

- [ ] Lexical search is persistent and incremental
- [ ] Stable chunk ids link ledger, FTS, and Chroma
- [ ] Index freshness is revision-based, not count-based
- [ ] Query text is safely compiled and result sizes are bounded
- [ ] FTS failures degrade to dense retrieval without query failure
- [ ] The old in-memory BM25 path is removed only after measured promotion
