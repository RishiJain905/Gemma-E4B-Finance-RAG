# 2.3.7.1 — Capability Inventory and Coverage Tool

## Objective

Answer questions about what the system knows from authoritative corpus metadata,
not from a sampled retrieval result or model memory.

Examples include:

- "What tickers do you know about?"
- "Which companies can you answer questions about?"
- "Do you cover Shopify?"
- "Which healthcare securities have SEC filings?"
- "What sources and data types are available for NVDA?"

The answer must distinguish security membership, stored evidence, enabled source
capability, freshness, and deep versus broad coverage. These concepts are related
but not interchangeable.

## Step 1: Define a bounded coverage read model

Add a Store-level read contract that projects the Phase 2.3 security universe,
coverage policies, corpus metadata, and source status into a stable response:

```text
total_securities
active_securities
coverage_tiers: broad | deep | sector
securities[]: security_id, ticker, name, active memberships, coverage tier
source_categories[]: configured, enabled, available, last terminal status
item_types[] and metric families[]
filters_applied
result_count, total_matching, complete, next_cursor
data_revision and universe_snapshot_at
```

`complete` is true only when the response contains the complete requested set.
The tool must never represent a limited page as the complete corpus.

For the expected Phase 2.3 universe (fewer than 1,000 active securities), an
explicit request for "all tickers" returns the complete sorted list. More detailed
rows remain paginated with an opaque cursor and hard limits.

## Step 2: Add focused Store queries

Expose read-only methods through `Store`; callers must not join SQLite tables or
scan Chroma directly:

- list/search securities by membership, sector, industry, tier, and active date;
- test whether one ticker/security is covered;
- summarize corpus/source/item-type coverage for one or more securities;
- list available metric families independently from document coverage;
- return bounded aggregate counts from Phase 2.3 accounting tables.

The methods use the canonical security registry from 2.3.1 and corpus ledger from
2.3.3. Before those migrations are available, a compatibility adapter may project
existing fundamentals and Chroma metadata, but it must mark the response
`coverage_basis="legacy_partial"`.

## Step 3: Register `describe_coverage`

Add one read-only tool rather than expanding the overloaded `list_metrics` tool.

Supported operations:

```text
summary
list_securities
contains_security
security_sources
list_sources
list_item_types
list_metrics
```

Arguments are explicit and bounded: `operation`, optional `ticker`, filters,
`limit`, and `cursor`. The dispatcher enforces a read-only ToolContext. The tool
makes no network or model call and cannot trigger ingestion.

Keep `list_metrics` temporarily for compatibility. It delegates its ticker/metric
inventory work to the new Store contract and is removed only after callers and
tests no longer depend on its older result shape.

## Step 4: Render deterministic coverage answers

Add deterministic templates for complete coverage results:

- full ticker list plus exact count for an all-ticker request;
- yes/no/partial coverage for one security, with the basis stated;
- source and item-type availability for one security;
- truthful pagination language when the result is intentionally bounded;
- explicit unavailable/partial language when the registry or source status is
  missing.

Coverage answers carry `answer_origin="deterministic_coverage"`, the Store
revision, and result-completeness metadata. They do not claim that a configured
provider has data for a security unless stored evidence or a successful source
status proves it.

## Failure behavior

- Missing Phase 2.3 tables: use the marked legacy compatibility projection.
- Corrupt/unavailable inventory: return a structured unavailable result; never
  fall through to model guessing.
- Stale source status: disclose its timestamp and status.
- Excessive result size: return a complete ticker-only view when possible,
  otherwise a page with `complete=false` and `next_cursor`.
- Unknown ticker: return `covered=false` plus resolver suggestions when available.

## Testing

- Ask for all tickers and compare the exact sorted list and count with the
  canonical active security registry.
- Prove a limited detail page reports `complete=false` and a cursor.
- Distinguish universe membership from actual stored evidence and enabled source
  capability.
- Filter by index, sector, coverage tier, item type, source category, and date.
- Simulate missing Phase 2.3 tables and verify marked legacy-partial behavior.
- Simulate Store failure and assert no model call or invented fallback answer.
- Assert the tool cannot invoke refresh or any write operation.

## Verification Checklist

- [ ] Coverage questions read canonical metadata rather than retrieval samples
- [ ] An all-ticker request is complete and exactly counted below the safe bound
- [ ] Every bounded response exposes completeness and pagination metadata
- [ ] Membership, evidence, source capability, and freshness remain distinct
- [ ] Failures produce truthful unavailable/partial answers without model guessing
- [ ] The tool is read-only, bounded, and network-free
