# 2.3.4.3 — Refresh Status, Backfills, and Operational Controls

## Objective

Provide safe commands and truthful status for initial population, routine daily
refresh, repair, and retention without mixing those workloads together.

## Work modes

### Bootstrap

Populate the universe and bounded history from an empty/new schema. Bootstrap is
explicit and resumable. Defaults are conservative:

- current index memberships plus membership observation date;
- recent SEC submissions/event history with a configured start date;
- configurable company-news window;
- configurable daily market-history window;
- current official macro catalog plus bounded history;
- no automatic full periodic-filing backfill for every broad security.

### Incremental refresh

The normal scheduler path uses TTLs, cursors, overlap windows, and budgets. It
does not infer that a missing API key or open circuit means the source is fresh.

### Repair/reindex

Retry stored `pending|error` normalization/indexing records without re-downloading
the source when enough metadata/content remains. Target by source, security,
item id, date range, or run id.

### Retention

Preview and apply configured narrative retention. Retention is never implied by
daily refresh.

## Step 1: Extend scheduler CLI safely

Add commands/options:

```text
python -m src.scheduler bootstrap [--source NAME] [--since YYYY-MM-DD] [--resume]
python -m src.scheduler daily [--source NAME] [--scope SCOPE] [--force]
python -m src.scheduler repair [--source NAME] [--limit N]
python -m src.scheduler retention --preview
python -m src.scheduler status [--source NAME] [--json]
```

Destructive retention requires explicit apply confirmation/flag and prints the
target cutoff/count first. `--force` bypasses freshness only, not quotas,
entitlements, circuit cooldown, or retention safeguards.

## Step 2: Expand run status

Store one run plus per-source summaries:

- mode, policy/config revision, start/end/duration;
- requested/completed/skipped/failed sources;
- partitions/items/requests/new/updated/duplicates;
- cursor before/after and quota remaining when known;
- freshness, last success, next due, cooldown/reset;
- safe terminal error class/message.

Keep historical run summaries bounded by retention. `cache_meta` remains the
compatibility freshness source while richer status uses the run/cursor tables.

## Step 3: Add coverage health

Status calculates, without network calls:

- active securities by index/scope/sector;
- securities with recent news/market/SEC coverage;
- never-fetched/stale/error partitions by source;
- indexing backlog and error counts;
- oldest/newest corpus dates and last successful refresh.

Coverage percentages always include a denominator and policy revision.

## Step 4: Integrate refresh tooling

The existing guarded refresh tool may request a bounded source/security refresh,
but it must use the same registry, budgets, circuit state, and maximum refreshes
per query. It cannot invoke bootstrap, retention, or a full broad-universe run.

## Testing

- Resume bootstrap after an interrupted partition without duplicating writes.
- Prove daily refresh never performs unrequested bootstrap history.
- Repair an indexing failure without a provider request.
- Preview retention with no mutations, then apply only the displayed eligible set.
- Report mixed success/rate-limit/missing-key status accurately.
- Reject unbounded refresh-tool requests.

## Verification Checklist

- [ ] Bootstrap, incremental, repair, and retention are distinct operations
- [ ] Every long-running operation is resumable and bounded
- [ ] Status reports cursors, budgets, coverage, backlog, and safe failures
- [ ] `--force` cannot bypass provider/safety limits
- [ ] Query tools cannot trigger bootstrap or full-universe refresh
- [ ] Status and health queries perform no external network work
