# 2.3.4.2 — Rate Limits, Circuit Breakers, and Failure Isolation

## Objective

Generalize the current GDELT rate-limit handling so provider-wide exhaustion
stops pointless work after bounded retries while every other source continues.

## Error classes

Normalize provider failures into:

- `authentication` — missing/invalid credential; no retry in the run;
- `entitlement` — endpoint unavailable on the account; no retry;
- `rate_limited` — HTTP 429/provider equivalent, with optional reset time;
- `quota_exhausted` — local daily budget or provider daily allowance consumed;
- `transient` — timeout, connection failure, or retryable 5xx;
- `contract` — malformed/unexpected response shape;
- `item` — one bad record inside an otherwise valid response;
- `permanent` — invalid request/resource.

Logs and status expose the class and safe message, never credentials or complete
provider responses.

## Step 1: Apply provider-level circuit semantics

Use the existing resilience primitives with source-specific policy:

- honor `Retry-After`/reset headers;
- retry transient/429 failures at most the configured limit (default three
  attempts total);
- cap sleep and jitter; no unbounded waits;
- after exhausted provider-wide 429/quota/auth/entitlement failure, open the
  source circuit for the run and skip remaining partitions;
- do not try the next ticker when the provider itself is unavailable;
- persist the reset/cooldown when safe so a later scheduler invocation can skip
  immediately.

This is the explicit generalized form of the GDELT behavior: after the bounded
attempts fail due to provider rate limiting, the run does not move from NVIDIA to
NVDA or to another ticker and repeat the same doomed request pattern.

## Step 2: Keep item and partition isolation

A malformed news row, unresolved security, bad SEC filing, or one 404 remains an
item/partition failure. Record it and continue within the source when the
provider is healthy.

The scheduler catches source-level failures, marks only that source stale/partial,
adds a bounded dead-letter record when appropriate, and proceeds to the next
registered source.

## Step 3: Make retry decisions observable

Each source result records:

- attempts, requests, accepted/rejected items;
- terminal status and normalized error class;
- retry/reset/circuit timestamps;
- last committed cursor;
- whether remaining work was skipped due to provider state.

Corpus Explorer refresh status may display these fields. Live Trace displays
retrieval-time source fallback only; ingestion runs do not become query traces.

## Step 4: Bound dead letters

Dead-letter identity includes source, partition, provider record id/cursor, error
class, first/last seen, and attempt count. Exact repeats update one record. A
provider-wide 429 creates one source/run entry, not hundreds of per-ticker rows.

## Testing

- Exhaust three 429 attempts and assert no later ticker/partition is requested.
- Honor numeric/date `Retry-After` under a mocked clock.
- Skip immediately during persisted cooldown and resume after expiry.
- Treat auth/entitlement failures as non-retryable.
- Continue past one malformed item and one permanent per-resource 404.
- Continue to the next source after a provider circuit opens.
- Deduplicate source-wide DLQ records.

## Verification Checklist

- [ ] Provider-wide failures stop remaining provider work after bounded attempts
- [ ] Per-item failures do not unnecessarily stop a healthy source
- [ ] One source failure never aborts the refresh batch
- [ ] Retry/reset/circuit state is persisted and visible
- [ ] Logs/status redact secrets and unbounded payloads
- [ ] DLQ growth is bounded for repeated provider-wide failures
