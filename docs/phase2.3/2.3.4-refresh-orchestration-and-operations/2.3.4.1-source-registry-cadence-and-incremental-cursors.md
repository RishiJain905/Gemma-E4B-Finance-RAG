# 2.3.4.1 — Source Registry, Cadence, and Incremental Cursors

## Objective

Scale the existing unified scheduler from a static source dictionary into a
validated, budget-aware registry while preserving its simple sequential,
fail-soft execution model.

## Step 1: Define a small source specification

Each source declares:

- stable name and capability group;
- enabled state and required environment variable, if any;
- coverage scope (`universe|broad|deep|sector|global`);
- cadence and allowed run modes;
- priority/order and optional dependencies;
- cursor kind (`date|timestamp|page_token|daily_index|none`);
- overlap window for late/revised records;
- request/minute and request/day budgets;
- batch size and maximum work items per run;
- retry/circuit policy name.

Configuration is validated at startup. Invalid source configuration disables
that source with a visible status; it does not crash unrelated sources.

Keep the scheduler implementation in-process. A data-driven registry does not
justify a queue, broker, or orchestration framework.

## Step 2: Persist cursors separately from freshness

Add `source_cursors` keyed by source plus logical partition, for example:

- SEC daily-index date globally;
- Finnhub last successful publication time per security;
- Massive market date globally;
- agency dataset release/vintage token;
- universe provider snapshot time.

Fields include cursor value/type, overlap value, last successful run id, updated
time, and version. `cache_meta` continues to describe freshness; a cursor is not
a freshness signal.

Advance a cursor only after all accepted records for its page/partition commit.
An overlap window intentionally refetches a small range and relies on idempotence.

## Step 3: Reserve budgets before work

Create a per-run budget object that tracks attempted/successful requests and the
provider's reported remaining/reset headers. Work selection must fit configured
daily and per-minute limits before a request starts.

For per-ticker news, schedule oldest-successful/never-fetched partitions first so
one repeated partial run eventually covers the entire universe. A forced run may
ignore TTL, but never ignores a provider quota or safety rate.

## Step 4: Preserve existing run modes

Keep `daily`, `hourly`, `weekly`, `all`, and `status`. Select registered sources
by cadence instead of hard-coded lists. Add optional `--source` and `--scope`
filters for controlled implementation/testing.

Daily defaults:

- universe snapshots when due;
- SEC incremental events;
- Finnhub company news;
- Massive daily market/corporate actions after the expected market window;
- official feeds when due;
- existing deep sources according to their current TTLs.

## Testing

- Validate registry entries and independently disable a missing-key source.
- Advance/rollback date, token, and per-security cursors transactionally.
- Refetch overlap windows and prove idempotent storage.
- Enforce minute/day/run budgets before requests.
- Fairly resume a partial per-security run on its next invocation.
- Keep legacy scheduler modes and per-source TTL skipping compatible.

## Verification Checklist

- [ ] Source behavior is configured in one registry
- [ ] Freshness and incremental cursor state remain separate
- [ ] Cursors advance only after committed records
- [ ] Forced refresh cannot bypass provider safety limits
- [ ] Partial runs resume fairly instead of restarting ticker one forever
- [ ] Existing scheduler commands remain available
