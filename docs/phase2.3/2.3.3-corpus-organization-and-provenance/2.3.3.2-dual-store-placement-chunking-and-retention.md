# 2.3.3.2 — Dual-Store Placement, Chunking, and Retention

## Objective

Place each new data type in the correct store, index narrative evidence under a
stable family, and control corpus growth with explicit retention rules.

## Placement matrix

| Data | SQLite | Chroma |
|---|---|---|
| Securities/memberships/aliases | Canonical rows | No |
| Daily OHLCV, rates, economic observations | Canonical rows/vintages | No |
| Corporate actions and classified event fields | Canonical rows | Optional linked narrative only |
| SEC filing/exhibit metadata | Canonical rows | Selected text/sections |
| News and API summaries | Metadata/provenance/index status | Headline + provider summary |
| Government/issuer releases | Metadata/provenance/index status | Release text or supplied summary |
| Refresh/cursor/run health | Canonical rows | No |

Embedding numeric rows wastes space and weakens exact-date/value retrieval. The
prompt pipeline should receive numeric data through structured facts/tools.

## Step 1: Establish stable document families

Every narrative `corpus_item_id` maps to one `document_family_id`. Chunks retain:

- corpus item, source category/name, provider record id;
- canonical security ids/tickers, index memberships, sector/industry;
- item/event type, form/item/exhibit where applicable;
- published/effective/as-of dates;
- parent/child chunk ids and ordinal;
- content hash, normalization version, authority tier.

Chunk ids remain stable while content is unchanged. Replacements delete the old
family only after the new normalized content is accepted.

## Step 2: Reuse existing chunking intentionally

- SEC periodic filings keep Phase 2.2 natural section hierarchy.
- Short news summaries and short releases remain one document unless they exceed
  the configured chunk threshold.
- Long government/issuer releases use the existing structure/sentence-aware
  chunker with parent metadata.
- Tables retained as text must keep headings and units with the chunk.
- No ingestion-time LLM summaries are added.

## Step 3: Define retention by evidence class

Defaults:

- SEC filings/exhibits, issuer releases, official government releases, events,
  actions, membership history, and observations: retain permanently;
- company news narratives: retain 24 months, configurable;
- expired news metadata/provenance: retain as a tombstone/count record when the
  narrative family is removed;
- raw network payloads: do not retain by default; sanitized fixtures are tests,
  not an operational archive;
- failed/unindexed metadata: retain until repaired or explicitly pruned.

Retention runs are explicit maintenance jobs, never part of a query. Deletions
bump the Store revision and remove only the targeted Chroma family.

## Step 4: Add storage accounting

Expose counts and approximate bytes by source category, source, item type,
security, year/month, and indexing state. This powers status and Corpus Explorer
without scanning all Chroma documents on every request.

## Testing

- Route every record family to the placement matrix.
- Prove no market/economic numeric observation creates a Chroma document.
- Preserve stable family/chunk ids on exact replay.
- Replace changed content without leaving old chunks or duplicate families.
- Expire news narratives at the cutoff while retaining a metadata tombstone.
- Keep permanent evidence classes untouched by news retention.
- Return bounded aggregate counts without a full corpus materialization.

## Verification Checklist

- [ ] Structured values remain queryable in SQLite and absent from embeddings
- [ ] Narrative chunks carry all required source/security/date facets
- [ ] Existing SEC hierarchy remains compatible
- [ ] Retention policy is explicit by item type
- [ ] Family replacement and deletion are atomic from the retrieval perspective
