# 2.3.6.1 — Schema, Configuration, and Backward-Compatible Migration

## Objective

Introduce Phase 2.3 tables/configuration without losing existing SQLite/Chroma
data or requiring all new sources to be enabled at once.

## Step 1: Add a lightweight migration runner

The current store creates tables and applies a few inline column migrations.
Phase 2.3 adds enough related tables that ordered, idempotent SQL migrations are
clearer. Add a small standard-library runner and `schema_migrations` table; do not
add Alembic or another migration dependency.

Migration order:

1. securities, aliases, memberships, reconciliation errors;
2. corpus items, item sources, and item-security links;
3. observations and events/actions;
4. source cursors, richer source runs, cooldown/circuit state;
5. indexes and aggregate-query support.

The canonical schema file and inline new-database fallback must converge on the
same final schema.

## Step 2: Backfill existing identities and corpus metadata

Create a resumable migration command that:

- creates securities from existing canonical ticker rows;
- attaches SEC CIKs where already known;
- preserves the current `core` list as deep coverage;
- creates `corpus_items` metadata for existing Chroma document families and SEC
  filings without re-embedding unchanged text;
- links existing fundamentals, CompanyFacts, filings, freshness, and documents
  to canonical security ids where resolvable;
- records ambiguous/orphan records for review instead of guessing;
- bumps the Store revision after each committed bounded batch.

The migration never deletes existing rows or Chroma families. It is safe to stop
and resume.

## Step 3: Add configuration without exposing secrets

Add documented configs:

- `configs/universe.yaml` — constituent providers/validation;
- `configs/coverage.yaml` — broad/deep/sector policies;
- `configs/sources.yaml` — cadence, budgets, cursor/retry policy;
- `configs/official_sources.yaml` — curated agency series/releases;
- existing storage/middleware configs — retention, taxonomy, graph limits.

Environment variables are referenced by name only. Configuration/status may
report `configured: true|false`, never values or partial key fingerprints.

## Step 4: Gate rollout additively

Feature switches default off by capability:

- universe refresh;
- SEC broad event discovery;
- company news;
- grouped market data/corporate actions;
- official macro/regulatory feeds;
- sector feeds;
- Phase 2.3 retrieval facets/ranking;
- Phase 2.3 Corpus Explorer projection.

Schema migration may land before sources are enabled. Disabling a source leaves
stored evidence queryable and does not roll back the schema.

## Step 5: Define rollback

- Disable the affected source/capability flag.
- Stop new Phase 2.3 scheduling.
- Preserve additive tables and existing indexed content.
- Restore Phase 2.2 retrieval/graph behavior through flags.
- Use an explicit maintenance command for data removal only after separate
  authorization; rollback itself is non-destructive.

## Testing

- Initialize from an empty database and from a representative Phase 2.2 database.
- Run every migration twice and assert no changes/errors on the second run.
- Interrupt/resume metadata backfill without duplicates or re-embedding.
- Preserve all existing counts and query results with Phase 2.3 flags off.
- Record and report orphan/ambiguous identities.
- Scan setup/status output to prove no secret values are emitted.
- Reopen migrated databases with current Store initialization repeatedly.

## Verification Checklist

- [ ] New and migrated databases converge on one schema version
- [ ] Migration is additive, idempotent, bounded, and resumable
- [ ] Existing Chroma content is not re-embedded when unchanged
- [ ] Ambiguous legacy records are reported, not guessed or dropped
- [ ] Missing keys disable only their sources
- [ ] Feature flags restore Phase 2.2 behavior without destructive rollback
