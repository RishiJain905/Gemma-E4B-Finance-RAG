# Phase 2.3.7 RAG Quality, Speed, and Storage Design

## Status

Approved for specification on 2026-07-14. This document records the design that
the numbered specs implement; it is not an implementation result.

## Problem

The Phase 2.3 source overhaul will substantially expand the corpus, but corpus
size alone does not solve answer quality or speed:

- capability questions such as "Which tickers do you know about?" can be
  answered from a retrieval sample and presented as exhaustive;
- indirect or verbose questions may not compile to all required answer
  obligations;
- Phase 2.2 can construct deterministic answers but still sends them through the
  expensive local generation path;
- the optional lexical index materializes the Chroma corpus in process and uses
  document count as its freshness signal;
- multiple implemented RAG capabilities remain disabled or only partially
  connected, creating permanent code/config uncertainty;
- a larger corpus raises a valid database question, but replacing stores before
  measuring the optimized current architecture would add scope and migration
  risk without evidence.

## Goals

- Return complete, exact, authoritative corpus inventories and counts.
- Improve routing for indirect, compound, and conversational questions.
- Avoid model generation when a typed answer is fully and safely determined.
- Make lexical retrieval persistent, incremental, revision-aware, and bounded.
- Give every dormant capability a measured promote/retain/remove decision.
- Establish a reproducible keep/replace gate for SQLite + Chroma.
- Preserve grounding, source isolation, rollback, and local-first operation.

## Non-goals

- An open-ended autonomous agent loop.
- Turning every qualitative finance question into a template.
- Replacing the local model, graph stack, or structured SQLite state.
- Adding a vector database only because the document count increased.
- Implementing multiple production storage adapters before a benchmark fails.
- Re-running embeddings solely to build the lexical index.

## Selected design

### 1. Separate catalog truth from retrieval relevance

Security membership, corpus coverage, source availability, metric families, and
exact counts are Store metadata questions. A new read-only coverage contract
uses the canonical security registry and corpus ledger. Every bounded result
states whether it is complete; top-k retrieval is never treated as an inventory.

### 2. Compile answer obligations, not only a broad intent label

The query plan records universe scope, operation, dimensions, time/as-of scope,
required completeness, qualitative needs, and evidence modes. A route succeeds
only when all obligations are covered. Catalog and structured lanes run before
general semantic retrieval when appropriate.

### 3. Add a guarded deterministic answer exit

Completely covered allowlisted requests can return typed templates with exact
values, periods, units, provenance, freshness, and completeness metadata. Any
partial, qualitative, conflicting, stale-policy, or failed-tool condition keeps
the grounded model path. This targets the dominant local generation latency
without weakening complex answers.

### 4. Replace process-local BM25 with SQLite FTS5

The corpus ledger, FTS rows, and Chroma chunks share stable chunk ids and one
revision contract. Ingestion applies incremental FTS deltas; search returns only
bounded candidate ids for hydration and existing RRF fusion. Revision mismatch
or FTS failure degrades to dense retrieval instead of failing the request.

### 5. Treat disabled features as decisions with expiry

Each Phase 2.2 RAG capability receives one disposition after an isolated
comparison:

- promote into a documented profile;
- retain temporarily with an owner, prerequisite, and Phase 2.3 expiry; or
- remove its code path, configuration, docs, tests, and exclusive dependency.

Profiles provide a small `legacy`, `recommended`, and `evaluation` surface rather
than requiring users to coordinate many independent flags.

### 6. Make database replacement conditional

Benchmark optimized SQLite + FTS5 + Chroma first at 100,000 seeded chunks using
precomputed embeddings. Measure quality, filtered retrieval, cold/warm latency,
memory, disk, mutation throughput, restart behavior, and reconciliation. Only a
hard failure after one bounded optimization pass or a newly approved operational
requirement triggers a pilot.

If triggered, LanceDB is the first embedded/local-first candidate. Qdrant is
considered only when operating a separate service is acceptable and useful.
Production migration remains a separately approved phase with rollback.

## Query flow

```text
question
  -> parse entities, intent, and answer obligations
  -> authoritative catalog needed? -> Store coverage tool
  -> exact structured work needed?  -> bounded read/calculation tools
  -> narrative evidence needed?     -> dense + FTS5 -> RRF -> optional rerank
  -> complete typed answer eligible?
       yes -> validate and return without generation
       no  -> grounded local-model generation
  -> evidence/citation validation and trace metadata
```

## Failure and rollback behavior

- Missing Phase 2.3 catalog tables use a labeled legacy-partial projection.
- Inventory failure returns unavailable/partial, never a model-invented list.
- Optional planning/rewrite failure falls back to deterministic compilation.
- FTS syntax, availability, or revision failure falls back to bounded dense
  retrieval and records degraded mode.
- Deterministic rendering failure falls back to generation exactly once.
- The legacy profile retains the pre-promotion behavior during rollout.
- Cross-store reconciliation detects and repairs identity drift before promotion.

## Success criteria

- Exact all-ticker set precision and recall are 1.0 with zero inventions.
- Capability-routing precision is at least 0.98.
- Indirect-query exact-plan accuracy improves at least 15 percentage points.
- Eligible deterministic answers make zero model calls and are at least 90%
  faster end-to-end.
- Existing nDCG@10 regresses by no more than 0.02.
- At 100,000 seeded items, warm lexical p95 is below 100 ms and hybrid p95 below
  250 ms on the documented reference machine.
- Every dormant feature has a final disposition before Phase 2.3 sign-off.
