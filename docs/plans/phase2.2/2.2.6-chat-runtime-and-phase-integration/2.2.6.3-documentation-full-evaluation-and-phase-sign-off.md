# 2.2.6.3 — Documentation, Full Evaluation & Phase Sign-Off

## Objective

Reconcile the authoritative docs with the implemented Phase 2.2 behavior, run
the complete offline verification gate, schedule rather than silently run the
GPU/model evaluation, and require a results/rollback decision for every
implemented feature before declaring Phase 2.2 complete.

## Why This Matters

Phase 2.1 documentation already drifts from code in streaming, configuration,
chunking, projection, and response metadata. A large architecture phase needs
one final contract across code, API docs, configuration, chat help, and
evaluation. Offline green tests are necessary but do not prove local-model
answer quality; live evaluation must be explicit because it consumes the GPU.

## Step 1: Reconcile authoritative documentation

Update:

- `docs/ARCHITECTURE.md` — conversational compiler, adaptive lanes, evidence
  ledger/grader, corrective bound, CompanyFacts, filing hierarchy, streaming,
  cache, and live graph when implemented;
- `docs/API.md` — history/session fields, orchestration/sufficiency/support
  metadata, stream events, evidence trace diagnostics, and graph endpoints;
- `docs/CONFIGURATION.md` — every Phase 2.1/2.2 key, default, environment
  override, bound, and rollback flag;
- `README.md` and `scripts/CHAT.md` — multiline/history/session commands,
  progress, graph URL, and capability display;
- `eval/README.md` — evidence-trace, conversation, compound, long-document,
  route, support, and latency evaluation procedures.

Remove or correct stale claims that streaming is reserved, fixed-character
chunking is active, SEC filing text is already in Chroma, or response fields do
not include Phase 2.1/2.2 additions.

**Files to modify:**
- `docs/ARCHITECTURE.md`
- `docs/API.md`
- `docs/CONFIGURATION.md`
- `README.md`
- `scripts/CHAT.md`
- `eval/README.md`

## Step 2: Require per-feature results

After each numbered feature is implemented, create that folder's `RESULTS.md`
with:

- commit/config/dataset/trace schema identifiers;
- offline gate result;
- live setup only when run;
- baseline and treatment metrics with denominators;
- latency/call/resource measurements;
- failure injection and rollback result;
- caveats and unresolved cases;
- explicit `ship enabled`, `ship disabled`, `blocked`, or `rollback` decision.

Do not create empty results files during planning. A feature without evaluated
results remains incomplete or explicitly deferred.

## Step 3: Run the full offline gate first

Run:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\verify.ps1
```

The gate runs ruff and offline tests only. It must end with `VERIFY: PASS`.
Do not start `chat.py`, middleware, scheduler, a browser, or llama-server as
part of this gate. Fix failures and rerun the full gate; a scoped test pass is
progress, not sign-off.

Also run static spec/doc validation that checks:

- every Phase 2.2 task path listed in `docs/plans/phase2.2/README.md` exists;
- each task has Objective, Why This Matters, Steps, Testing, and Verification
  Checklist;
- local Markdown links resolve;
- config/API keys documented match implemented names.

## Step 4: Schedule GPU/model evaluation explicitly

When the user confirms the GPU is free:

1. Record model build, context, tools/Jinja, feature flags, corpus watermark,
   and baseline digest.
2. Run the repaired strict/graded single-turn baseline.
3. Run conversation/compound, adaptive/corrective, long-document, citation,
   and latency comparisons.
4. Keep raw run artifacts outside git and write summarized `RESULTS.md` files.
5. Stop the stack after the scheduled run.

Until then, mark live-model gates `PENDING — GPU not authorized`, never
`PASS`. Offline completion must not be presented as live answer-quality proof.

## Step 5: Complete the requirement audit

Before sign-off, prove:

- confirmed evidence-delivery and prompt-policy defects are fixed;
- chat accepts bounded history and multiline questions;
- raw questions remain intact and follow-ups compile correctly;
- simple/standard/complex lanes obey all call/round limits;
- deterministic tools cannot select writes;
- evidence sufficiency, correction, citations, and numeric validation are
  observable and fail soft;
- CompanyFacts and filing hierarchy are authoritative, reversible, and
  provenance-preserving;
- streaming/caching/live graph remain bounded and local-safe;
- every implemented feature has a rollback flag and results decision;
- no secrets, model paths, `.env`, data directory, or raw run artifacts are
  committed.

Create `docs/plans/phase2.2/PHASE2.2-COMPLETION.md` only after every required
item is proven. List deferred items separately; do not relabel them complete.

## Testing

Documentation tests should parse files/config/schema without starting services.
API schema tests use FastAPI models directly or a mocked app client. The final
offline gate remains the authoritative code completion check.

## Verification Checklist

- [ ] Architecture, API, configuration, chat, README, and eval docs agree
- [ ] No stale Phase 1/2.1 behavior claims remain
- [ ] Every implemented feature has evidence-backed `RESULTS.md`
- [ ] Full offline gate ends in `VERIFY: PASS`
- [ ] No service, browser, network ingestor, or model is started by offline sign-off
- [ ] Live-model gates remain pending until GPU use is authorized
- [ ] Rollback flags and failure behavior are tested
- [ ] Requirement-by-requirement evidence is recorded before completion
- [ ] Completion document is created only after all required evidence exists
