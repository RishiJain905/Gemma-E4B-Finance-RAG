# 2.2.6.2 — Versioned Retrieval Cache & Prompt Efficiency

## Objective

Add a small in-memory retrieval cache whose key includes a persisted data
revision/freshness watermark, make prompt prefixes reusable, and measure
llama-server prompt-cache reuse before enabling it. Never use semantic
similarity to reuse volatile final finance answers.

## Why This Matters

Phase 2.1 already caches exact query embeddings, while generation and prefill
still dominate latency. Repeated retrieval plans and stable prompt prefixes can
avoid duplicate work, but a cache that ignores ingestion changes can return
stale facts/news. Finance correctness requires exact invalidation before hit
rate.

## Step 1: Define a cross-process data revision

Add a single-row `store_revision` table to SQLite with monotonic integer
revision and `updated_at`. Expose:

- `Store.retrieval_revision() -> int`;
- `Store.bump_retrieval_revision(reason)`.

Every Store facade mutation that can change model-visible facts/documents bumps
the revision before mutation begins; a failed write may cause an extra cache
miss but can never leave stale cache entries valid. Direct ingestors must use
the Store facade or explicitly bump through one documented helper.

Keep Chroma count and per-source freshness watermarks in cache telemetry for
diagnosis, but do not rely on count alone because same-count replacements are
possible.

**Files to modify:**
- `docs/phase1.2/schema.sql`
- `src/storage/sqlite_store.py`
- `src/storage/store.py`
- ingestion tests touching Store writes

## Step 2: Add a bounded exact retrieval cache

Create `src/middleware/retrieval_cache.py` with a thread-safe LRU+TTL cache.

Key fields:

- compiled retrieval query and validated plan fields;
- lane, subqueries, filters, top-k, lexical/rerank settings;
- embedding/reranker/config fingerprints;
- store revision;
- relevant freshness/as-of requirement.

Values contain normalized pre-prompt evidence and retrieval metadata, never
the final generated answer. Copy/freeze values so callers cannot mutate cached
records.

Defaults:

- `enable_retrieval_cache: false` initially;
- `retrieval_cache_max_entries: 256`;
- `retrieval_cache_ttl_s: 300` as a secondary bound;
- `retrieval_cache_max_value_chars` with a bounded documented default;
- clear cache when feature/config/model fingerprints change;
- no cache lookup for requests that explicitly refresh or require evidence
  newer than the current watermark.

Cache failures are misses. They never fail a query.

**Files to create:**
- `src/middleware/retrieval_cache.py`

**Files to modify:**
- `src/middleware/adaptive_orchestrator.py`
- `src/middleware/config.py`
- `configs/middleware.yaml`
- `tests/test_retrieval_cache.py`

## Step 3: Keep prompt prefixes stable and compact

Centralize the fixed system policy in 2.2.1.1 and render prompt sections in a
stable order:

1. system policy;
2. compact conversation context;
3. task/query-plan obligations;
4. evidence ledger;
5. untouched raw question;
6. output/citation contract.

Remove duplicate policy prose and compact tool results to only model-required
fields. Record prompt characters/estimated tokens, evidence characters, and
fixed-prefix digest.

Add optional `llama_cache_prompt` configuration. When enabled and supported,
send the official llama-server prompt-reuse field on the final request and
capture returned reused-token timings. If the backend rejects it, disable it
for the process and retry the plain payload once, following existing fail-soft
capability behavior.

**Files to modify:**
- `src/middleware/prompt_policy.py`
- `src/middleware/prompt_augmenter.py`
- `src/middleware/app.py`
- `src/middleware/config.py`
- `configs/middleware.yaml`
- `tests/test_latency_optimizations.py`

## Step 4: Explicitly prohibit unsafe answer caching

Do not implement semantic final-answer caching for:

- prices, news, sentiment, freshness, estimates, guidance, or “latest” asks;
- different tickers/periods whose embeddings are nearby;
- requests with refresh enabled;
- conversation turns whose compiled plan differs.

An optional exact answer cache for immutable, explicitly date-bounded requests
is outside this task and requires its own evidence watermark/citation contract.
Document the prohibition so it is not later added as an unreviewed
optimization.

## Step 5: Evaluate correctness and latency

Offline tests prove exact invalidation for fact insert/update, document add/
replace/delete, refresh, configuration change, TTL expiry, explicit refresh,
and concurrent reads. Inject a clock and fake Store; do not sleep.

Live evaluation, only when GPU is explicitly available, reports cold/warm p50/
p95 retrieval, TTFT, total latency, cache hit/miss reasons, prompt tokens, and
llama-server reused tokens.

Promotion gates:

- zero stale cache hits in invalidation tests;
- cold-query p95 regresses by no more than 5%;
- warm repeated-query TTFT improves at least 30% when prompt reuse is supported;
- cache memory remains within configured entry/size limits;
- volatile requests never hit a final-answer cache.

## Testing

Create/extend offline tests for revision bumps before Store mutations,
same-count document replacement, fact update, refresh, TTL expiry, model/config
fingerprint change, explicit cache bypass, immutable copies, LRU eviction,
concurrent lookup, and backend capability fallback. Inject clocks, stores, and
HTTP responses; never sleep or contact llama-server. Prompt-reuse performance
is recorded only in the separately authorized live evaluation.

## Verification Checklist

- [ ] Store revision changes before every model-visible mutation
- [ ] Retrieval cache key includes query plan, config/model fingerprints, and revision
- [ ] Same-count replacements invalidate correctly
- [ ] Cache is bounded, copied/frozen, thread-safe, and fail-soft
- [ ] Refresh/newer-than requests bypass cache
- [ ] Prompt policy is single-owner and section order is stable
- [ ] llama-server prompt reuse is optional, measured, and capability-fallback safe
- [ ] No unsafe semantic final-answer cache is introduced
- [ ] Correctness gates precede latency promotion
