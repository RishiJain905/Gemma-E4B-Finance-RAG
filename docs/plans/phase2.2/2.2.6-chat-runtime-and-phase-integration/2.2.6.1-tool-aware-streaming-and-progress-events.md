# 2.2.6.1 — Tool-Aware Streaming & Progress Events

## Objective

Keep the bounded tool/planning rounds non-streaming, then stream the final
answer synthesis and emit safe progress events so `chat.py` and the live graph
can show what the query pipeline is doing. Enabling tools must no longer disable
streaming for the entire request.

## Why This Matters

The current streaming endpoint rejects requests whenever tools are enabled, so
the TUI advertises streaming, probes once, and silently falls back to a long
spinner. The local model may spend tens of seconds in prefill/generation. Stage
and tool progress plus final token streaming improves perceived responsiveness
without attempting to stream incomplete tool-call JSON.

## Step 1: Define one backward-compatible event contract

Create `src/middleware/stream_events.py` with serialization helpers for:

- `query_started` — query id and timestamp;
- `stage` — `compile|route|retrieve|grade|correct|pack|generate|validate` plus
  `started|completed|fallback`;
- `tool_started` — safe tool name and subquery id;
- `tool_completed` — tool name, status, row/item count, elapsed time;
- `token` — existing token delta shape;
- `metadata` — existing terminal response plus new orchestration/support fields;
- `error` — terminal/nonterminal flag and safe message.

Every event has `schema_version`, `query_id`, monotonic `sequence`, and
timestamp. Keep existing `token`, `metadata`, and `error` payloads compatible so
older clients continue to work.

Define one internal `QueryEvent` and request-scoped emitter. Query stages emit
once; separate serializers produce the redacted chat SSE event and, when
enabled, the richer but still allowlisted graph-observer delta in 2.2.7. Do not
instrument the pipeline twice for two UIs.

Do not emit raw tool arguments, full tool results, prompts, document bodies,
secrets, or HTTP headers in progress events. Exact evidence remains available
only through the opt-in trace/localhost observer contracts.

## Step 2: Separate tool planning from final streaming

Refactor the bounded model/tool loop into two phases:

1. Non-streaming planning/tool execution until the model returns no further
   tool call or the configured iteration budget is consumed.
2. One final answer request with the completed tool messages and `stream=true`.

Deterministic tool routes from 2.2.3.2 skip phase 1 and go directly to final
streaming when generation is required. A tool/planner error follows the existing
fail-soft fallback and emits a stage fallback event.

If final streaming fails before any token, fall back once to the existing
non-streaming final answer. If it fails after tokens were emitted, send a
terminal error and do not append a second conflicting answer.

## Step 3: Report effective capability

`/health.capabilities.streaming` must reflect whether the deployment can serve
the streaming endpoint, not whether the current request has completed tool
planning. Add `streaming_tool_final=true` when the new path is active.

The stream endpoint returns:

- 404/405 only when the capability/route is genuinely unavailable;
- 422 for request validation without changing client capability state;
- normal SSE stage/tool events for tools-enabled requests.

Update `ChatSession` to cache “stream unsupported” only for 404/405. Validation,
auth, conflict, and transient server errors remain visible and retryable.

Add feature controls:

- `enable_tool_final_streaming: bool = False` initially;
- `enable_stream_progress_events: bool = False` initially;
- `stream_progress_include_counts: bool = True`.

When both new controls are false, preserve the current streaming/tool behavior
for regression comparison. Promote them only after the event/client tests and
live TTFT check pass.

## Step 4: Render restrained progress in chat

TTY default display:

```text
  resolve -> hybrid retrieval -> query_facts (12 rows) -> answer
```

Update one line in place rather than printing a log stream. `/verbose on` may
show elapsed stage timings and corrective reasons. Non-TTY output omits animated
updates and prints only terminal answer/metadata.

Unknown future event types are ignored. No ANSI escape sequences are emitted
when colors are disabled.

**Files to modify:**
- `scripts/chat.py`
- `scripts/CHAT.md`
- `tests/test_chat_client.py`

## Testing

Offline tests cover event ordering/schema, tools-enabled final streaming,
deterministic-tool streaming, no-token fallback, midstream terminal error,
iteration cap, redaction, unknown events, non-TTY output, effective health
capability, and 422 not poisoning streaming support.

## Verification Checklist

- [ ] Tools-enabled requests can stream the final synthesis
- [ ] Planning/tool rounds remain bounded and non-streaming
- [ ] Progress events are versioned, ordered, query-scoped, and redacted
- [ ] Existing token/metadata/error consumers remain compatible
- [ ] Only 404/405 marks streaming unavailable in the client
- [ ] No duplicate answer is emitted after a midstream failure
- [ ] TTY progress is concise and non-TTY output remains clean
- [ ] Tests use mocked SSE/model/tool boundaries only
