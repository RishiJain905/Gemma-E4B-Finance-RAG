# 2.2.5.2 — SEC Filing Text & Parent-Child Indexing

## Objective

Ensure newly processed SEC filings place their actual section text in ChromaDB
with deterministic document, section, and chunk relationships. Preserve
headings and filing provenance so retrieval can find precise child chunks and
later reconstruct only the relevant surrounding section.

## Why This Matters

Phase 2.1 introduced structure-aware chunking, but its migration found no SEC
filing text in the vector corpus. SQLite tracks filings and processing state,
yet the most valuable long-form evidence is not available to document
retrieval. More advanced routing cannot recover evidence that was never
indexed.

## Step 1: Define a deterministic filing-section contract

Create `src/sec/filing_sections.py` with `FilingSection`:

- `accession`, `ticker`, `form`, `filing_date`, and report period;
- canonical section key and visible heading;
- ordered section index;
- normalized nonblank text;
- source URL and local parsed-file path;
- stable `document_id = sec:{accession}:{section_key}`.

Add `split_filing_sections(parsed_text, filing_metadata)`. Reuse headings and
section markers produced by `filing_parser.py`; do not ask the model to
rediscover structure. Preserve heading text in every section body. Unknown
headings use deterministic ordinal keys rather than being discarded.

Filter navigation boilerplate, repeated headers, and empty sections with
explicit rules. Never delete tables or numeric text merely because it is
formatted densely.

**Files to create:**
- `src/sec/filing_sections.py`

**Files to modify:**
- `src/sec/filing_parser.py`
- `tests/test_filing_parser.py`
- `tests/test_filing_sections.py`

## Step 2: Index section parents through the existing chunker

Add `Store.add_filing_sections(sections)` and route every section through
`ChromaStore.add_document()` with the configured structural chunker. Do not
create a second embedding path.

Each stored child chunk must retain:

```text
source=sec_filing
ticker
accession
form
filing_date
report_period
section_key
section_heading
section_index
parent_id=sec:{accession}:{section_key}
document_id/child chunk id
chunk_index and chunk_count
source_url
```

The parent identifier represents one filing section, not the entire 10-K.
Chroma child ids remain deterministic and idempotent. Reprocessing the same
filing updates/replaces its section family without producing duplicates.

## Step 3: Wire indexing into the filing processor

After a filing is fetched and parsed successfully:

1. Build validated `FilingSection` rows.
2. Index all usable sections.
3. Confirm the expected parent/chunk counts.
4. Mark the filing `parsed` only after its durable parsed artifact and vector
   section index are both successful.
5. Store/index errors on the filing/ingestion log and leave it retryable.

Per-filing failure remains isolated. One malformed filing must not stop other
tickers or scheduler sources. If Chroma is unavailable, preserve the parsed
artifact and record an `index_pending` state/reason rather than falsely marking
the vector step complete.

Do not generate an LLM summary as a prerequisite for section indexing.

**Files to modify:**
- `src/sec/filing_processor.py`
- `src/sec/scheduler.py`
- `src/storage/sqlite_store.py`

If a new state is needed, add it additively and keep legacy `parsed` rows
readable. Document the migration in 2.2.5.3.

## Step 4: Add read APIs for section families

Add bounded Chroma/Store methods:

- `get_section_chunks(parent_id, *, limit, offset=0)`;
- `get_adjacent_sections(accession, section_index, *, before=1, after=1)`;
- `count_filing_sections(accession=None)`;
- `delete_filing_section_family(parent_id)` for idempotent replacement.

Methods return canonical `document` bodies and complete metadata. They must not
scan or return an entire corpus when a parent/accession filter is available.
Limit and offset have safe maxima.

**Files to modify:**
- `src/storage/chroma_store.py`
- `src/storage/store.py`
- `tests/test_chroma_store.py`

## Step 5: Add rollout controls and observability

Configuration:

- `sec.index_filing_text: false` initially;
- `sec.max_sections_per_filing` with a safe high bound;
- `sec.max_section_chars` for parser sanity only, never silent truncation;
- `sec.index_forms: [10-K, 10-Q, 8-K]`.

Log parent sections/chunks written, skipped empty sections, replacements,
pending indexes, embedding failures, and elapsed time. Add counts to scheduler
status without requiring a live embedding request.

**Files to create:**
- `configs/sec.yaml`

## Testing

Use local parsed filing fixtures containing headings, prose, tables, duplicate
headers, and empty sections. Mock the embedding function.

Tests must prove:

- headings remain in indexed bodies;
- stable section/chunk ids are idempotent;
- reprocessing replaces rather than duplicates a section family;
- every child has complete accession/section provenance;
- a Chroma failure leaves an index-pending/retryable state;
- one filing failure does not stop another;
- no model summary/generation call occurs;
- bounded family/neighbor reads do not scan unrelated filings.

## Verification Checklist

- [ ] New SEC filings index actual section text, not metadata-only placeholders
- [ ] Section headings and table/numeric text are preserved
- [ ] Parent/child ids and metadata are deterministic and idempotent
- [ ] Existing structural chunking/embedding path is reused
- [ ] Filing state distinguishes parsed artifacts from completed vector indexing
- [ ] Per-filing failures remain isolated and retryable
- [ ] Bounded family/neighbor read APIs exist
- [ ] No ingestion-time LLM summary or GraphRAG dependency is introduced
- [ ] All tests use local fixtures and mocked embeddings
