# 2.2.4.2 — Selective Query Decomposition & Fusion

## Objective

Decompose only genuinely compound or low-coverage plans into at most two
derived finance-specific subqueries, retrieve each through its appropriate
modality, and fuse/deduplicate results while keeping the original resolved query
as the strongest signal.

## Why This Matters

One embedding for a long request can dilute exact entities and operations, but
generating several paraphrases for every query adds latency and query drift.
The repository already has RRF. The smallest useful upgrade is selective
decomposition by ticker, metric, period, or evidence obligation—not default
free-form RAG-Fusion.

## Step 1: Define deterministic decomposition rules

Add `decompose_plan(plan, missing_obligations=None)` to
`src/middleware/query_plan.py`.

Decompose when:

- independently answerable clauses require different modalities;
- multiple entities have distinct metrics/periods;
- a comparison requires one aligned lookup per entity;
- a trend plus risk/news/explanation needs structured and document evidence;
- the evidence grader requests `run_derived_subqueries`.

Do not decompose a single coherent fact lookup, one qualitative topic, or a
question already covered by the standard lane.

Every derived `QuerySubquery` contains:

- stable id `sq1` or `sq2`;
- parent `sq0`;
- validated entities, metrics, periods, intents, and retrieval mode;
- deterministic query text;
- evidence obligations it covers;
- `derivation_source` and reason code.

The complete plan remains capped at three subqueries including `sq0`.

**Files to modify:**
- `src/middleware/query_plan.py`
- `tests/test_query_plan.py`

## Step 2: Validate derived-query drift

A derived query is valid only when every entity, metric, period, and operation
comes from the validated parent plan or known aliases. Reject:

- invented tickers or company names;
- new numeric thresholds/dates;
- broader market topics not requested;
- duplicated paraphrases with the same obligations;
- empty or stopword-only queries.

If the optional planner from 2.2.2.2 proposes subqueries, pass them through the
same validator and keep at most two that add distinct obligation coverage. On
rejection, use deterministic subqueries or `sq0` alone.

Record drift reason codes in the evidence trace.

**Files to modify:**
- `src/middleware/query_plan.py`
- `src/middleware/query_rewriter.py`
- `tests/test_query_rewriter.py`

## Step 3: Execute specialized retrieval per subquery

The adaptive orchestrator maps retrieval modes:

- exact facts/calculation -> deterministic tools/SQLite;
- company qualitative -> current hybrid vector + BM25;
- news/risk/sentiment -> document channel with matching metadata filters;
- macro -> FRED facts plus documents only when requested;
- projection -> estimates/tools plus qualitative context only when requested;
- long filing section -> hierarchy expansion from 2.2.5.3.

Batch independent embedding requests when the embedding backend supports it.
SQLite/tool and lexical/vector work may run concurrently, but preserve stable
result ordering after collection. One batch of all subqueries counts as one
retrieval round.

**Files to modify:**
- `src/middleware/adaptive_orchestrator.py`
- `src/middleware/retriever.py`
- `tests/test_adaptive_orchestrator.py`

## Step 4: Fuse with original-query priority and coverage

Extend RRF with a small optional weighted input contract while preserving the
current two-list function for legacy callers:

- original `sq0` weight: `1.0`;
- deterministic derived subquery weight: `0.8`;
- optional planner-derived subquery weight: `0.6`;
- vector and lexical channel contributions remain visible;
- exact structured evidence is not ranked against documents; it is attached to
  its obligation directly.

After fusion:

1. Deduplicate by stable document id and parent/chunk identity.
2. Reserve at least one result for every covered subquery before filling
   remaining score-ranked slots.
3. Prefer authoritative/fresh evidence when scores are comparable.
4. Keep `subquery_ids`, channel ranks, weights, and fused score on each result.
5. Pass candidates through the conditional re-ranker at most once.

**Files to modify:**
- `src/middleware/retriever.py`
- `src/middleware/lexical_index.py` only if batch scoring needs a public seam
- `tests/test_retrieval_integration.py`

## Step 5: Evaluate recall, drift, and cost

Compare standard single-query retrieval with selective decomposition on the
compound set. Report:

- Recall@5/10 and nDCG@10;
- subquestion evidence coverage;
- generated/derived query drift rate;
- candidate and final context counts;
- embedding/retrieval/reranker/model calls;
- retrieval and total latency;
- answer correctness and citation support.

Promotion gates:

- complex-query correctness improves at least 10 percentage points;
- compound subquestion evidence coverage improves at least 10 points;
- drift rate remains below 0.05;
- single-query nDCG@10 regresses by no more than 0.02;
- simple queries generate no derived subqueries;
- no plan exceeds three total queries or two rounds.

**Files to modify:**
- `eval/run_eval.py`
- `eval/metrics.py`
- `eval/score.py`
- `tests/test_eval_harness.py`

## Testing

Add offline tests for fact+risk, trend+comparison, two tickers with different
periods, macro+company, and already-sufficient simple queries. Verify original
weight priority, obligation slot reservation, parent deduplication, stable
ordering, planner drift rejection, and call/round caps.

## Verification Checklist

- [ ] Decomposition runs only for compound or low-coverage plans
- [ ] At most two derived queries supplement the original `sq0`
- [ ] Every derived field comes from the validated plan/catalog
- [ ] Original query has the strongest fusion weight
- [ ] Structured evidence remains attached to obligations instead of document ranks
- [ ] Fusion preserves subquery/channel provenance and coverage
- [ ] Parent/chunk duplicates are removed before context packing
- [ ] Simple queries add zero decomposition cost
- [ ] Drift, recall, quality, and latency gates are measured
