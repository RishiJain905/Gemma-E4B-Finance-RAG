# 2.1.4.1 — Tool Framework & Function-Calling Plumbing

## Objective

Stand up the mechanism that lets the TraceAlchemy model **call tools**: a tool
registry (name, JSON schema, handler), the request/response wiring to
llama-server's OpenAI-compatible `tools` / `tool_calls`, and a bounded
tool-execution loop in the middleware.

## Why This Matters

Every analytical capability (query_facts, estimates, refresh) is useless until
the model can actually invoke it. This task is the foundation the rest of 2.1.4
and 2.1.5 build on. It also answers the recurring "let the model run the jobs"
request.

## Step 1: Tool registry

Create `src/middleware/tools/__init__.py` with a registry:

```python
# src/middleware/tools/base.py (sketch)
from dataclasses import dataclass
from typing import Callable

@dataclass
class Tool:
    name: str
    description: str
    parameters: dict          # JSON Schema
    handler: Callable         # (store, **kwargs) -> dict
    write: bool = False        # state-changing? (guarded)

REGISTRY: dict[str, Tool] = {}

def register(tool: Tool): REGISTRY[tool.name] = tool
def openai_schema() -> list[dict]:
    return [{"type": "function", "function": {
        "name": t.name, "description": t.description, "parameters": t.parameters}}
        for t in REGISTRY.values()]
```

**Files to create:** `src/middleware/tools/base.py`,
`src/middleware/tools/__init__.py`.

## Step 2: Tool-calling loop in `_call_model`

Extend `src/middleware/app.py::_call_model` to:
1. Send `tools=openai_schema()` (when tools are enabled) with the chat request.
2. If the response contains `tool_calls`, dispatch each to its handler
   (`REGISTRY[name].handler(store, **args)`), append `role: "tool"` messages
   with the JSON results, and re-call the model.
3. Loop up to `config.max_tool_iterations` (e.g. 3) to prevent runaway loops.
4. Return the final assistant message.

```python
# sketch
for _ in range(config.max_tool_iterations):
    resp = await model_client.post(endpoint, json={**payload, "tools": schema})
    msg = resp.json()["choices"][0]["message"]
    if not msg.get("tool_calls"):
        return msg["content"], _extract_citations(msg["content"])
    messages.append(msg)
    for call in msg["tool_calls"]:
        result = dispatch_tool(call, store)   # guarded for write tools
        messages.append({"role": "tool", "tool_call_id": call["id"],
                         "content": json.dumps(result)})
```

**Files to modify:** `src/middleware/app.py`, `src/middleware/config.py`
(`enable_tools: bool`, `max_tool_iterations: int`).

## Step 3: Guarding & safety

- `write=True` tools (e.g. `refresh_data`, 2.1.4.4) are only dispatched when
  `config.allow_write_tools` is set; otherwise return a "write tools disabled"
  result so the model can explain instead of acting.
- Validate tool args against each tool's JSON schema before calling; return a
  structured error on mismatch (the model can recover).
- Log every tool call (name + args + duration) for observability.

## Step 4: Graceful degradation

If the served model build doesn't support `tools` (older llama-server),
detect the error once and **disable tool-calling for the session**, falling
back to the plain prompt path. Never hard-fail a query because tools are
unsupported.

## Testing

Create `tests/test_tool_framework.py`:
- `test_register_and_schema` — registering a tool exposes a valid OpenAI schema.
- `test_dispatch_calls_handler` — a fake `tool_calls` response routes to the
  handler with parsed args (mock the model client).
- `test_tool_loop_terminates` — a model that always returns tool_calls stops at
  `max_tool_iterations`.
- `test_write_tool_guarded` — a `write=True` tool is refused when
  `allow_write_tools=False`.
- `test_arg_validation_error` — bad args yield a structured error, not a crash.
- `test_tools_unsupported_fallback` — model rejecting `tools` falls back to the
  plain path and still answers.
