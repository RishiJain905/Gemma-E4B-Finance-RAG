# 2.1.4.4 — Guarded `refresh_data` Tool & End-to-End

## Objective

Add the one **state-changing** tool — `refresh_data` — so the model can fetch
missing/stale data mid-conversation, behind strong guards. Then validate the
whole tool suite end-to-end through `/query` and the chat client, and measure
with the 2.1.1 harness.

## Why This Matters

This is the payoff for "tell the model to run the jobs": when the model detects
it lacks fresh data, it can trigger a refresh, then answer. Because it mutates
state and is slow, it needs guarding the read tools don't.

## Step 1: `refresh_data` tool

Add to `src/middleware/tools/data_tools.py`, `write=True`:
- Params: `ticker` (required), `sources` (optional list; default all stale).
- Handler calls the existing `_refresh_ticker_sources` / `/refresh` logic
  (reuse, don't reimplement).
- Returns `{refreshed, errors, duration_s}` so the model can report what it did.

```python
def refresh_data_handler(store, ticker, sources=None):
    from src.middleware.app import _refresh_ticker_sources, _normalize_sources, store as gstore
    logical = _normalize_sources(sources) or _stale_sources(gstore, ticker)
    refreshed, errors = _refresh_ticker_sources(ticker.upper(), logical)
    return {"ticker": ticker.upper(), "refreshed": refreshed, "errors": errors}
```

## Step 2: Guards

- Only dispatched when `config.allow_write_tools` is true (from 2.1.4.1);
  otherwise the loop returns "write tools disabled" and the model explains.
- **Per-conversation rate limit** (e.g. max N refreshes per query) to prevent a
  loop from hammering upstream APIs.
- Respect the source API limits documented in `potential-ideas.md` — never let
  the model trigger a full `all`/scheduler run via this tool; restrict to
  per-ticker refresh.
- Log prominently (it's a side effect).

**Files to modify:** `src/middleware/tools/data_tools.py`,
`src/middleware/config.py` (`allow_write_tools`, `max_refreshes_per_query`).

## Step 3: End-to-end wiring & docs

- Confirm the full suite (query_facts, list_metrics, read tools, refresh_data)
  is registered and advertised in `openai_schema()`.
- Update `docs/API.md` (note `/query` may now invoke tools) and
  `docs/ARCHITECTURE.md` (tool-calling flow diagram).
- The chat client (`scripts/chat.py`) needs no change to benefit, but add a
  `/tools` command that prints the registered tool list for visibility.

**Files to modify:** `docs/API.md`, `docs/ARCHITECTURE.md`, `scripts/chat.py`.

## Step 4: Evaluate

Run the 2.1.1 harness with tools **on vs. off**; record in
`docs/Phase2.1/2.1.4-structured-analytical-tooling/RESULTS.md`. Expect the
analytical/aggregation and untracked-data cases to flip from refusal to correct
answers, with acceptable added latency from tool round-trips.

## Testing

Create `tests/test_refresh_tool_and_e2e.py`:
- `test_refresh_tool_guarded` — with `allow_write_tools=False`, the tool is
  refused; with true, `_refresh_ticker_sources` is called (patched).
- `test_refresh_rate_limit` — exceeding `max_refreshes_per_query` is blocked.
- `test_refresh_cannot_trigger_full_scheduler` — only per-ticker refresh paths
  are reachable.
- `test_end_to_end_tool_query` (mark `integration`) — a question requiring
  `query_facts` triggers the tool loop and returns a grounded answer
  (model client + handlers stubbed where needed).
- Regression: with `enable_tools=False`, `/query` behaves exactly as pre-2.1.4.
