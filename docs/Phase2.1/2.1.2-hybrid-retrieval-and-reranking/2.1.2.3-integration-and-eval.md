# 2.1.2.3 — Integration, Config & Evaluation

## Objective

Wire the lexical channel (2.1.2.1) and re-ranker (2.1.2.2) cleanly into the
live `/query` and `/search` paths, expose the knobs in config, refresh the
lexical index after ingestion, and prove the end-to-end quality gain with the
2.1.1 harness.

## Why This Matters

The pieces only pay off when they're on the real request path, stay fresh as
data changes, and are measured. This task closes those loops.

## Step 1: Retriever assembles the full pipeline

`Retriever.retrieve()` final shape:
1. Vector search (existing) → top `rerank_candidates`.
2. BM25 lexical search → top `rerank_candidates`.
3. RRF fuse.
4. Cross-encoder re-rank → top `rerank_top_n` (= `top_k_documents`).
5. Return docs (with `rerank_score`) + the existing SQLite facts.

Each stage is individually toggleable so you can A/B in the harness:
`enable_lexical`, `enable_reranker`.

**Files to modify:** `src/middleware/retriever.py`, `src/middleware/config.py`,
`configs/middleware.yaml` (document the new keys).

## Step 2: Keep the lexical index fresh

The BM25 index is built from the corpus and goes stale as documents are added.
- Add a lightweight rebuild trigger: rebuild on middleware startup, and after
  `/refresh` / scheduler runs (call `LexicalIndex.refresh()`), or rebuild lazily
  when chroma's `count()` changes since last build.
- Document the chosen strategy in `docs/ARCHITECTURE.md`.

**Files to modify:** `src/middleware/app.py` (build on startup; refresh hook),
`docs/ARCHITECTURE.md`.

## Step 3: Surface re-ranking in responses (optional, useful)

Include `rerank_score` in `/search` document results so you can inspect ranking
quality. Add `retrieval_strategy` to the `/query` response metadata
(`vector` | `hybrid` | `hybrid+rerank`) for observability.

**Files to modify:** `src/middleware/models.py`, `src/middleware/app.py`.

## Step 4: Evaluate

Run the 2.1.1 harness in three configs and record in
`docs/Phase2.1/2.1.2-hybrid-retrieval-and-reranking/RESULTS.md`:
1. vector-only (baseline)
2. + lexical/RRF
3. + re-ranker

Compare retrieval_hit_rate, faithfulness, keyword_coverage, latency. Ship only
if (2) and (3) beat (1) without unacceptable latency.

## Testing

Create `tests/test_retrieval_integration.py` (mark `integration`):
- `test_query_hybrid_path` — patch lexical + reranker, assert the retriever
  calls both and returns reranked docs through `/query`.
- `test_search_includes_rerank_score` — `/search` exposes `rerank_score`.
- `test_strategy_flag` — response metadata reports the active strategy.
- `test_index_refresh_after_refresh_endpoint` — refreshing data rebuilds the
  lexical index (patch `LexicalIndex.refresh`, assert called).
- Regression: existing middleware tests still pass with features **disabled**
  (defaults must preserve current behavior unless explicitly enabled).

## Verification Checklist

- [ ] Full pipeline (vector → BM25 → RRF → rerank) on the `/query` path
- [ ] Each stage independently toggleable via config/`middleware.yaml`
- [ ] Lexical index rebuilds on startup and after ingestion/refresh
- [ ] `/search` exposes `rerank_score`; `/query` reports `retrieval_strategy`
- [ ] `RESULTS.md` records the 3-way eval comparison
- [ ] `tests/test_retrieval_integration.py` passes; existing tests unaffected
- [ ] No answer-quality or latency regression per the 2.1.1 gate
