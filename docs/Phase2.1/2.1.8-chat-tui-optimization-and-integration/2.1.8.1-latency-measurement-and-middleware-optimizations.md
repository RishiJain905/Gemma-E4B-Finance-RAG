# 2.1.8.1 — Latency Measurement & Middleware Optimizations

## Objective

Measure where `/query` time actually goes, then remove the avoidable
middleware overhead. The biggest single cost is model token generation (not
fixable in the middleware), but there are real removable round-trips and
repeated work on the request path.

## Why This Matters

"It feels slow" needs a breakdown before optimizing. Once measured, several
wins are easy: the query path currently makes an **extra HTTP round-trip to
`:8087/health` on every request** before calling the model, re-reads freshness
each query, and re-embeds identical queries. Cutting these shaves real latency
without touching generation speed.

## Step 1: Add a latency breakdown

Instrument `src/middleware/app.py::query` to time each stage and return them:

```python
timings = {}
def _stage(name, t0): timings[name] = round((time.time()-t0)*1000, 1)
# intent_parse, freshness_check, retrieval (embedding + chroma + sqlite),
# prompt_build, model_call
```

Add `timings: dict` to `QueryResponse` (optional, behind
`config.return_timings`, default true in dev). This is the diagnostic that tells
you whether the bottleneck is retrieval, embedding, or the model.

**Files to modify:** `src/middleware/app.py`, `src/middleware/models.py`,
`src/middleware/retriever.py` (return sub-timings).

## Step 2: Cache the model-health check

Today `query` calls `await _check_model_health()` (an HTTP GET to
`:8087/health`) on every request before `_call_model`. Replace with a
**short-TTL cache** (e.g. 10s) so a burst of queries doesn't each pay a health
round-trip. Also: if `_call_model` itself succeeds, we *know* the model is up —
treat a successful call as a health refresh.

```python
_model_health = {"ok": False, "ts": 0.0}
async def _check_model_health(ttl=10.0):
    now = time.monotonic()
    if now - _model_health["ts"] < ttl:
        return _model_health["ok"]
    ... # do the real check, update cache
```

**Files to modify:** `src/middleware/app.py`.

## Step 3: Lighten `/health`

The enhanced `/health` builds a `UnifiedScheduler` and loops 6 tickers'
freshness on every call (the chat client hits it on startup). Cache the
scheduler status + freshness summary for a few seconds, and build the scheduler
once (module-level/lazy) instead of per request.

**Files to modify:** `src/middleware/app.py`.

## Step 4: Query embedding cache

Retrieval embeds the query via an HTTP call to `:8087/embeddings` every time.
Add a small LRU cache (keyed by normalized query text) in the embedding
function / retriever so repeated or similar queries skip the round-trip. Bound
the cache size; it's an in-process optimization only.

**Files to modify:** `src/storage/chroma_store.py` (or a thin cache wrapper),
`src/middleware/config.py` (`embedding_cache_size`).

## Step 5: Confirm connection reuse to the model

`model_client` is a persistent `httpx.AsyncClient` (good — keep-alive already).
Verify no per-request client creation crept in for embeddings; if the
`ChromaStore` embedding function opens a client per call, make it persistent.

**Files to modify:** `src/storage/chroma_store.py` (reuse one `httpx.Client`).

## Testing

Create `tests/test_latency_optimizations.py`:
- `test_timings_present` — `/query` response includes per-stage `timings`.
- `test_health_check_cached` — two quick `query` calls trigger only one real
  health request (patch the health call; assert call count == 1 within TTL).
- `test_health_cache_expires` — after TTL, it re-checks.
- `test_embedding_cache_hit` — embedding the same query twice calls the
  endpoint once (patch the embed client).
- `test_no_behavior_change` — answers/citations identical with caching on/off.

Use the 2.1.1 harness to record an avg-latency before/after in `RESULTS.md`
(expect a drop in the non-generation stages).
