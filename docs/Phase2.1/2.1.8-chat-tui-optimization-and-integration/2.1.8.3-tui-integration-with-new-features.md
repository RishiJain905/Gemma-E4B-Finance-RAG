# 2.1.8.3 — Keep the TUI in Sync With All New Features

## Objective

Make `scripts/chat.py` the single, coherent front door that surfaces every
Phase 2.1 addition: tool calls, grounding mode, projection answers,
fetch-on-miss notices, retrieval strategy, and resolved-ticker confirmation.
Consolidate the per-feature chat.py touch-points so the TUI never drifts behind
the backend.

## Why This Matters

Several 2.1 specs each add a small chat.py touch (`/tools` in 2.1.4.4, grounding
display in 2.1.7.1, `fetched_on_miss` in 2.1.6.2, `timings` in 2.1.8.1). Done
piecemeal they'll drift or conflict. This task is the integration checkpoint
that wires them together consistently and verifies the TUI reflects the full
system.

## Step 1: Render the enriched `/query` response

Update the answer renderer to show, when present:
- **Grounding mode** (`grounded|partial|general|refused`) — a small colored tag
  so you can see *why* an answer looks the way it does (2.1.7).
- **Tools used** — if the response reports tool calls, list them
  (`used: query_facts, get_price_targets`) (2.1.4).
- **Retrieval strategy** (`vector|hybrid|hybrid+rerank`) (2.1.2).
- **fetched_on_miss** — "fetched live data for BB" (2.1.6).
- **Resolved ticker** — when the resolver mapped a name/typo, confirm it
  ("interpreting as BlackBerry / BB") (2.1.6).

Make rendering **defensive**: every field is optional, so the same chat.py works
against any middleware version (older servers simply omit fields).

**Files to modify:** `scripts/chat.py`.

## Step 2: New / updated commands

- `/tools` — list registered tools (from 2.1.4) the model can call.
- `/grounding strict|graded` — flip `answer_policy` per session (sends the
  preference to `/query` if the server supports it).
- `/eval` — kick off the 2.1.1 harness against the running server and print the
  summary (optional convenience).
- Update `/help` to document all of the above.

**Files to modify:** `scripts/chat.py`.

## Step 3: Config awareness

On startup, fetch `/health` (now cached, 2.1.8.1) and show which capabilities
are active (tools on/off, streaming on/off, answer_policy) so the user knows
what the session supports. Degrade silently for fields the server doesn't
return.

**Files to modify:** `scripts/chat.py`, optionally `/health` to report a
`capabilities` block (`src/middleware/app.py`, `models.py`).

## Step 4: Docs

Refresh the README "Interactive chat" section and add a short
`scripts/CHAT.md` documenting every command and what each metadata tag means.

**Files to modify:** `README.md`; **create:** `scripts/CHAT.md`.

## Testing

Create/extend `tests/test_chat_client.py`:
- `test_renders_grounding_tag` — response with `grounding=partial` prints the tag.
- `test_renders_tools_used` — tool-call metadata is listed.
- `test_renders_fetched_on_miss` — `fetched_on_miss=["BB"]` prints the notice.
- `test_resolved_ticker_confirmation` — a resolved name/typo is echoed.
- `test_defensive_against_missing_fields` — a minimal (old-server) response
  renders without KeyErrors.
- `test_tools_command` — `/tools` queries and lists tools (mock endpoint).
- `test_help_lists_new_commands` — `/help` includes the new commands.
