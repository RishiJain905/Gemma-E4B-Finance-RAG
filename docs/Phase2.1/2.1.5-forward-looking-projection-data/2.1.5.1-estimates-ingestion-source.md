# 2.1.5.1 — Analyst Estimates & Price-Target Ingestion

## Objective

Add a new ingestion source that pulls **forward-looking analyst consensus** —
revenue/EPS estimates and price targets (high/low/mean) — and stores them as
**forward-dated facts**, distinct from realized historicals.

## Why This Matters

The store only holds historical/current facts, so the model can't ground a
"what to expect" answer and (correctly) refuses. Ingesting analyst consensus
gives it sourced, forward-looking data to reason over instead of fabricating.

## Step 1: Estimates ingestor

Create `src/macros/estimates_ingestor.py` with an `EstimatesIngestor` mirroring
the existing ingestor pattern (`store`, config, `fetch_for_ticker`,
`fetch_all_core`, cache-fresh marking).

Source priority (free-tier first; configurable):
1. **yfinance** (already a dependency, no key) — `Ticker.get_earnings_estimate`,
   `Ticker.get_revenue_estimate`, `Ticker.analyst_price_targets`,
   `Ticker.recommendations`. Zero-cost starting point.
2. **Financial Modeling Prep** — Financial Estimates + Price Target Consensus
   (needs `FMP_API_KEY`).
3. **Finnhub** — estimates + recommendation trends (needs `FINNHUB_API_KEY`).

Keys resolved via `src/utils/env.load_env()` (same pattern as FRED), config in
`configs/estimates.yaml` (`provider: yfinance|fmp|finnhub`, delays, retries).

**Files to create:** `src/macros/estimates_ingestor.py`,
`configs/estimates.yaml`.

## Step 2: Forward-dated fact schema

Store estimates as fundamentals with future periods and a distinct
`source_type="estimates"`, e.g.:

| metric | example value | period |
|--------|---------------|--------|
| `estimate_revenue` | 30.1e9 | `FY2026E` |
| `estimate_eps` | 4.10 | `2026-Q3E` |
| `price_target_mean` | 185.0 | `2026-06E` |
| `price_target_high` / `price_target_low` | 220 / 150 | `2026-06E` |
| `num_analysts` | 42 | `2026-06E` |
| `recommendation_mean` | 1.8 | `2026-06E` |

The `E` suffix and `source_type="estimates"` keep forecasts queryable but
clearly separable from realized facts (important so `query_facts` and the
answer policy never conflate them).

**Files to modify:** none to the schema (reuses `fundamentals`); document the
convention in `docs/ARCHITECTURE.md`.

## Step 3: Register with the scheduler

Add `estimates` to `UnifiedScheduler.SOURCES` (weight after fundamentals) and to
the appropriate cadence (daily or weekly), plus `FRESHNESS_SOURCES` in
`Store` and the `_SOURCE_ALIASES` map in the middleware refresh path — mirroring
exactly how `ir_pages` was wired in Phase 1.8.1.

**Files to modify:** `src/scheduler/__init__.py`, `src/storage/store.py`,
`src/middleware/app.py`, `configs/watchlist.yaml` (TTL key `estimates`).
