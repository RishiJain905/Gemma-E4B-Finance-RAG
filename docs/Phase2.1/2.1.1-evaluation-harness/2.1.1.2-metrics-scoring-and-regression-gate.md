# 2.1.1.2 — Metrics, Scoring & Regression Gate

## Objective

Turn raw run artifacts from 2.1.1.1 into **scores**: retrieval quality
(hit-rate / precision@k), answer faithfulness and relevance, intent/ticker
detection accuracy, and a refusal rate. Produce a human-readable report and a
machine-checkable **regression gate** so a change that drops quality fails loudly.

## Why This Matters

Numbers make the scoreboard actionable. A faithfulness score lets you ship
re-ranking only if it actually helps; a refusal-rate metric quantifies the
"too strict" problem (2.1.7); intent accuracy catches parser regressions.

## Step 1: Implement metrics

Create `eval/metrics.py` with functions that score a run artifact:

- **`intent_accuracy`** — `detected_intent == case.expected_intent` over cases
  that declare one.
- **`ticker_accuracy`** — `detected_ticker == case.expected_ticker`.
- **`retrieval_hit_rate`** — fraction of cases where at least one retrieved
  source matches `expected_sources` (or `facts_used + documents_used > 0` when
  no expected sources are given).
- **`keyword_coverage`** — fraction of `must_mention` terms present in the answer.
- **`refusal_rate`** — fraction of answers matching a refusal pattern
  (e.g. "don't have enough data"). Tracks over-strictness.
- **`faithfulness` / `answer_relevance`** — LLM-as-judge: call the local model
  (`:8087`) with the question, the retrieved context, and the answer, asking for
  a 0–1 score. Keep judge prompts in `eval/judge_prompts.py`. Gracefully skip
  (mark `null`) when the model is unavailable.

```python
# eval/metrics.py (sketch)
REFUSAL_MARKERS = ("don't have enough data", "i do not have enough", "cannot answer")

def refusal_rate(rows):
    n = len(rows)
    refused = sum(1 for r in rows if any(m in r["answer"].lower() for m in REFUSAL_MARKERS))
    return refused / n if n else 0.0
```

**Files to create:**
- `eval/metrics.py`
- `eval/judge_prompts.py`

## Step 2: Scoring CLI + report

Extend `eval/run_eval.py` (or add `eval/score.py`) to compute all metrics for a
run and emit:
- `eval/runs/<ts>.summary.json` — machine-readable metrics block.
- console table — per-category and overall scores.
- optional `eval/runs/<ts>.report.md` — readable diff vs. the previous run.

```
=== Eval summary (2026-..-..) ===
intent_accuracy      0.92
ticker_accuracy      0.88
retrieval_hit_rate   0.81
keyword_coverage     0.74
refusal_rate         0.18   (lower is better)
faithfulness (judge) 0.83
answer_relevance     0.79
```

## Step 3: Regression gate

Add `eval/gate.py` that loads the latest summary and a committed baseline
(`eval/baseline.json`) and **exits non-zero** if any metric regresses beyond a
tolerance (e.g. faithfulness drops > 0.05, refusal_rate rises > 0.05). This is
what you run before/after each Phase 2.1 feature and (optionally) in CI.

```bash
python eval/run_eval.py && python eval/score.py && python eval/gate.py
```

**Files to create:**
- `eval/score.py`
- `eval/gate.py`
- `eval/baseline.json` (committed; regenerated intentionally)

## Testing

Add to `tests/test_eval_harness.py`:
- `test_refusal_rate` — synthetic rows produce the expected ratio.
- `test_retrieval_hit_rate` — rows with/without matching sources score correctly.
- `test_keyword_coverage` — partial/!full keyword presence.
- `test_gate_passes_on_baseline` — identical run vs. baseline passes.
- `test_gate_fails_on_regression` — a degraded summary trips the gate (exit 1).
- LLM-judge tests mock the model client (no live dependency in unit tests).
