# 2.1.3.2 — Re-embedding Migration & Evaluation

## Objective

Re-chunk and re-embed the existing ChromaDB corpus under the new strategy
(2.1.3.1) without data loss, with an idempotent migration, and confirm the
change improves (or at least doesn't regress) retrieval via the 2.1.1 harness.

## Why This Matters

Changing chunking only helps documents that are re-embedded. Existing docs were
stored under the old fixed-window scheme, so they need a controlled migration —
done safely, repeatably, and measured.

## Step 1: Migration script

Create `scripts/rechunk_corpus.py` that:
1. Reads every document group from chroma (by `parent_id`, falling back to id).
2. Reconstructs the original text (join old chunks in order) — or, preferably,
   re-fetches source text where still available.
3. Deletes the old chunk entries for that parent.
4. Re-adds via `ChromaStore.add_document` (new chunker).
5. Is **idempotent** (safe to re-run) and supports `--ticker`, `--source`,
   `--dry-run`, and a `--limit` for incremental batches.

```bash
python scripts/rechunk_corpus.py --dry-run            # report what would change
python scripts/rechunk_corpus.py --source sec         # migrate one source
python scripts/rechunk_corpus.py                      # full migration
```

Re-embedding hits the `:8087` embeddings endpoint — batch and respect the
existing embedding batch size; log progress and a final count.

**Files to create:** `scripts/rechunk_corpus.py`

## Step 2: Safety

- Back up `data/chroma/` before a full run (document the copy step).
- Process per-parent so a mid-run failure leaves a consistent store (no
  half-deleted parents); use a manifest of completed parent_ids to resume.
- `--dry-run` prints old vs. new chunk counts without writing.

## Step 3: Evaluate before/after

Run the 2.1.1 harness pre- and post-migration; record in
`docs/Phase2.1/2.1.3-smarter-chunking/RESULTS.md`:
retrieval_hit_rate, faithfulness, avg chunks/doc, avg chunk length. Confirm no
regression (expect a modest retrieval gain, especially with the 2.1.2 re-ranker).

## Testing

Create `tests/test_rechunk_migration.py`:
- `test_dry_run_no_writes` — `--dry-run` leaves the collection unchanged
  (patch chroma; assert no add/delete calls).
- `test_migration_idempotent` — running twice yields the same final chunk set.
- `test_parent_grouping` — old `{id}#{i}` entries are grouped by `parent_id`
  and replaced as a unit.
- `test_resume_skips_completed` — parents in the manifest are skipped.
- Use a stubbed/in-memory chroma + stubbed embedder; mark live re-embed
  exercises as `integration`/`slow`.

## Verification Checklist

- [ ] `scripts/rechunk_corpus.py` re-chunks + re-embeds by parent, idempotently
- [ ] Supports `--dry-run`, `--source`, `--ticker`, `--limit`, resume manifest
- [ ] Per-parent processing keeps the store consistent on failure
- [ ] Backup step documented; `data/chroma/` unaffected on `--dry-run`
- [ ] `RESULTS.md` records before/after eval metrics
- [ ] `tests/test_rechunk_migration.py` passes
- [ ] Post-migration eval shows no retrieval regression
