# 2.2.1.3 — Conversational & Compound-Query Golden Set

## Objective

Extend the golden set and runner beyond concise, independent questions. Add
versioned fixtures and deterministic metrics for multi-turn follow-ups, verbose
wording, compound requests, multiple tickers, explicit and carried
timeframes, stale data, and genuinely unanswerable questions.

## Why This Matters

The existing golden set mostly rewards single-turn questions that already fit
the intent parser. It cannot measure the user's reported failure mode: natural,
longer questions and follow-ups require restating every entity, metric, and
period. It also under-measures comparison coverage and cannot detect
cross-session leakage or partial answers to compound requests.

## Step 1: Define two compatible fixture formats

Keep `eval/golden/finance_qa.jsonl` for single-turn cases and extend its schema
with optional fields:

- `subquestions` — stable ids for each required part of a compound question.
- `expected_tickers` — ordered ticker set for multi-company questions.
- `expected_metrics` and `expected_timeframe`.
- `expected_grounding` and `requires_stale_disclosure`.
- `answerability` — `answerable|partial|unanswerable`.
- `paraphrase_group` — links a verbose question to its concise equivalent.

Create `eval/golden/finance_conversations.jsonl` with one conversation per
line:

```json
{
  "id": "conv-followup-nvda-001",
  "category": "follow_up",
  "turns": [
    {"question": "Show NVDA revenue for FY2025.", "expected_tickers": ["NVDA"],
     "expected_metrics": ["total_revenue"], "expected_timeframe": "FY2025"},
    {"question": "What about AMD?", "expected_tickers": ["AMD"],
     "expected_metrics": ["total_revenue"], "expected_timeframe": "FY2025"}
  ]
}
```

Every turn may declare `expected_carryover` for `ticker`, `metrics`, and
`timeframe`. Fixture ids and turn ids must be unique and stable.

## Step 2: Add a balanced challenge set

Add at least:

- 12 conversations and 30 total turns, including pronouns, “what about,” “same
  period,” entity changes, and explicit context resets.
- 6 verbose/concise paraphrase pairs with identical expected retrieval intent.
- 6 compound questions with two or three independently scored subquestions.
- 6 multi-ticker questions, including comparisons and rank/filter requests.
- 6 timeframe cases spanning explicit quarter/year, relative latest/last, and
  carry-forward.
- 4 stale-data cases that require a visible freshness warning.
- 4 unanswerable cases that must not contain invented financial figures.

Categories may overlap, but the validation report must print counts for every
dimension so one large category cannot hide a missing one. Use stable fixture
expectations and seeded/mock data only; do not encode values that change with
live markets.

**Files to modify:**
- `eval/golden/finance_qa.jsonl`
- `eval/golden/finance_conversations.jsonl`
- `eval/golden/README.md`

## Step 3: Run conversations without server-owned state

Extend `eval/run_eval.py` to process conversation turns sequentially. The
runner owns the completed-turn history and sends it with the next request using
the 2.2.2.1 request contract. The middleware remains stateless.

Write one result row per turn with:

- `conversation_id` and `turn_index`;
- `raw_question` and `retrieval_query`;
- `history_sent` count;
- expected versus resolved tickers, metrics, and timeframe;
- subquestion ids and answer coverage;
- exact evidence trace from 2.2.1.2.

Start every conversation with an empty history. Provide an injected
`query_fn` for deterministic tests, and interleave two conversations in one
test to prove histories never cross.

**Files to modify:**
- `eval/run_eval.py`
- `eval/README.md`
- `tests/test_eval_harness.py`

## Step 4: Add deterministic conversational metrics

Implement in `eval/metrics.py`:

- `entity_carryover_accuracy`.
- `metric_carryover_accuracy`.
- `timeframe_carryover_accuracy`.
- `verbose_paraphrase_parity` — verbose and concise cases resolve to the same
  normalized retrieval plan.
- `compound_subquestion_coverage` — fraction of required parts addressed.
- `stale_disclosure_rate`.
- `unanswerable_numeric_hallucination_rate`.
- `cross_session_leakage_rate`.

Metric functions operate on captured structured fields and fixture
expectations. Only answer coverage may use an injected judge; entity/timeframe,
staleness, leakage, and unsupported-number checks must be deterministic.
Report overall and per-category denominators.

**Files to modify:**
- `eval/metrics.py`
- `eval/score.py`
- `eval/gate.py`
- `tests/test_eval_harness.py`

## Step 5: Define Phase 2.2 acceptance gates

Add the new metrics to the graded baseline after 2.2.2 is implemented. Phase
2.2 conversational-query work is ready to ship only when:

- entity, metric, and timeframe carryover accuracy are each at least 0.90;
- verbose paraphrase parity is at least 0.90;
- compound subquestion coverage is at least 0.85;
- stale disclosure rate is 1.00;
- unanswerable numeric hallucination rate is 0.00;
- cross-session leakage rate is 0.00;
- existing single-turn intent/ticker/retrieval gates do not regress beyond
  their approved tolerances.

The gate must fail when any required category has zero eligible fixtures.

**Files to modify:**
- `eval/gate.py`
- `eval/baselines/graded.json`
- `eval/README.md`
- `tests/test_eval_harness.py`

## Testing

Add offline tests for fixture validation, category minimums, sequential history,
interleaved session isolation, each new metric's pass/fail boundary, missing
category failure, and mixed single-turn/conversation run artifacts. Use fake
responses and exact structured expectations; do not call the middleware,
upstream services, or an LLM.

## Verification Checklist

- [ ] Single-turn fixtures support compound, multi-ticker, timeframe, stale, and answerability expectations
- [ ] A separate versioned conversation file contains at least 12 conversations / 30 turns
- [ ] Verbose paraphrases are measured against concise equivalents
- [ ] Conversation history is runner-owned and reset between conversations
- [ ] Result rows preserve raw question, retrieval query, expected context, and trace
- [ ] Carryover, compound coverage, staleness, unanswerable, and leakage metrics exist
- [ ] Every new metric reports a denominator and fails on missing required coverage
- [ ] Measurable Phase 2.2 thresholds are enforced without weakening existing gates
- [ ] All fixtures and tests are deterministic and offline-safe
