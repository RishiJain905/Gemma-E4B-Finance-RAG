# 2.2.1.2 — Exact Evidence Trace & Policy-Aware Scoring

## Objective

Capture the exact model-visible system prompt, augmented user prompt, normalized
facts/documents, and tool results for each evaluated answer. Replace the
truncated second retrieval pass with this trace and score grounded
faithfulness separately from graded-policy compliance so the 2.1.7 gate
compares like with like.

## Why This Matters

The current live runner re-runs retrieval after `/query`, caps judge context at
three documents × 600 characters, and cannot see tool results. The model may
answer from evidence the judge never receives. At the same time, strict
refusals inflate faithfulness while labeled general answers are skipped. This
measurement flaw, rather than a demonstrated policy defect, is what blocked
2.1.7.

## Step 1: Define an opt-in evidence trace

Create `src/middleware/evidence_trace.py` with a serializable
`EvidenceTrace` record and no external dependencies. Use schema version 1 with
these stable fields:

```json
{
  "schema_version": 1,
  "answer_policy": "graded",
  "grounding_level": "partial",
  "raw_question": "...",
  "retrieval_query": "...",
  "system_prompt": "...",
  "user_prompt": "...",
  "facts": [],
  "documents": [],
  "tool_results": []
}
```

`facts` and `documents` contain exactly the usable rows formatted into the
prompt, with full provenance and untruncated body text. `tool_results` records
each dispatched tool name, validated arguments, and the exact JSON result
appended as a `role=tool` message. Do not include secrets, HTTP headers, tool
schemas, or data that was not shown to the model.

Add `include_evidence_trace: bool = false` to `QueryRequest` and optional
`evidence_trace` to `QueryResponse`. The trace is omitted by default and is
included only for explicit evaluation requests. Streaming terminal metadata
must follow the same opt-in behavior.

## Step 2: Capture what the model actually saw

Create one trace collector in `_build_query_context` after evidence
normalization from 2.2.1.1. Populate its system and user prompts from the exact
messages sent to llama-server. During the bounded tool loop, append a tool
result only after central dispatch returns and immediately before the matching
`role=tool` message is appended.

The trace must represent the successful answer path:

- Plain call: system prompt + augmented user prompt + usable retrieval evidence.
- Tool call: the same retrieval evidence plus every tool result used before the
  final answer.
- Tools-unsupported fallback: record the final plain-call messages, not the
  abandoned unsupported attempt.
- Degraded answer: mark `model_available=false` in the run row and do not claim
  model-visible evidence.

Keep collection request-scoped. Concurrent requests and separate evaluations
must never share facts, documents, or tool results.

## Step 3: Make the eval runner consume the trace

Update `eval/run_eval.py` so live requests send
`include_evidence_trace=true` and persist the returned trace in each JSONL row.
Remove `_capture_context_and_sources` from the live path and stop re-running
retrieval to reconstruct context. Derive `retrieved_sources` from traced
facts, documents, and tool results.

Keep a direct/offline backend, but make it use the same evidence helpers,
prompt-policy builder, and trace schema as the middleware. A row with a model
answer and a missing/incomplete trace is an evaluation error, not silently
scorable context.

Add these stable run fields:

- `evidence_trace`
- `trace_complete`
- `answer_policy`
- `grounding`
- `dataset_digest`

`dataset_digest` is a SHA-256 of the committed golden inputs used for the run.
Use the standard library only.

## Step 4: Separate grounded faithfulness from policy compliance

Update `eval/metrics.py` and `eval/judge_prompts.py`:

- `grounded_faithfulness` scores only `grounded` and `partial` answers against
  the exact trace, including tool results.
- `policy_compliance` scores all four modes. Grounded/partial answers must stay
  within evidence; general answers must carry the required label and
  verification caveat and must not invent specific figures; refusals must be
  reserved for missing/unsafe/unanswerable cases.
- Refused and general answers do not enter the
  `grounded_faithfulness` denominator, so refusals cannot inflate it.
- Missing traces fail eligibility and are reported as `trace_errors`; they are
  never treated as faithful.

Keep `answer_relevance` and `refusal_rate`, but report denominators and
`n_eligible` for every metric. Use mocked judge outputs in unit tests.

## Step 5: Version and gate baselines correctly

Create policy-specific baseline paths:

- `eval/baselines/strict.json`
- `eval/baselines/graded.json`

Each baseline records `schema_version`, `trace_schema_version`,
`answer_policy`, `dataset_digest`, metric values, tolerances, and eligible
case counts. Extend `eval/score.py --set-baseline` and `eval/gate.py` with an
explicit `--policy strict|graded` selector.

The gate must fail before metric comparison when:

- current and baseline policies differ;
- trace or score schema versions differ;
- dataset digests differ;
- any answerable model row lacks a complete trace;
- an eligible metric denominator drops unexpectedly.

Re-baselining remains an explicit reviewed action; never overwrite a baseline
during a normal run. The 2.1.7 unblock gate is: 100% complete traces for
model-produced answers, tool evidence visible to the judge, no refusal-derived
faithfulness inflation, and no grounded-faithfulness regression beyond the
approved graded-policy tolerance.
