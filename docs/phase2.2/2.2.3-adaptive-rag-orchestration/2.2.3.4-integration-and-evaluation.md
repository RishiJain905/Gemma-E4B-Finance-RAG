# 2.2.3.4 — Adaptive Orchestration Integration & Evaluation

## Objective

Integrate the query plan, deterministic finance router, and bounded adaptive
orchestrator into the real `/query` and `/query/stream` paths behind one feature
flag. Expose route/budget metadata, keep the legacy path intact, and compare
quality and latency before enabling adaptive behavior by default.

## Why This Matters

The Phase 2.2 components only help when normal and streaming requests use the
same compiled question, lane decision, tool evidence, and context budget. A
piecemeal integration would recreate the drift already seen between prompt,
evaluation, and streaming paths. This task is the promotion checkpoint: it
proves the adaptive path is bounded, observable, and measurably better.

## Step 1: Add one request-path switch

Refactor `_build_query_context()` so both endpoints select one of two complete
paths:

- `enable_adaptive_rag=false` — current `IntentParser -> Retriever ->
  PromptAugmenter` behavior;
- `enable_adaptive_rag=true` — conversation compiler -> `QueryPlan` ->
  deterministic route -> `AdaptiveOrchestrator` -> selected evidence ->
  `PromptAugmenter`.

Do not scatter feature-flag checks across the retriever and prompt builder.
Choose the path once, then return the same context keys required by normal and
streaming answer functions.

If adaptive compilation/orchestration raises, record `adaptive_fallback` and
run the legacy path with the untouched raw question. The query must not fail
because the new layer failed.

**Files to modify:**
- `src/middleware/app.py`
- `src/middleware/adaptive_orchestrator.py`
- `tests/test_adaptive_orchestrator.py`
- `tests/test_middleware.py`

## Step 2: Expose bounded route metadata

Add optional `orchestration` metadata to `QueryResponse` and streaming terminal
metadata:

```json
{
  "lane": "complex",
  "reason_codes": ["multi_entity", "mixed_modalities"],
  "subqueries_executed": 3,
  "retrieval_rounds": 1,
  "planning_calls": 0,
  "reranker_calls": 1,
  "deterministic_tools": ["query_facts"],
  "context_chars": 11240,
  "evidence_dropped": 7,
  "fallback_reason": null
}
```

Metadata reports actual counters, not configured maxima. Preserve the existing
`retrieval_strategy`, `tools_used`, timings, grounding, and freshness fields.
Include the compiled retrieval query only when request diagnostics/evidence
trace is explicitly enabled.

Update `/health.capabilities` with `adaptive_rag` and
`deterministic_tool_routing` effective booleans.

**Files to modify:**
- `src/middleware/models.py`
- `src/middleware/app.py`
- `scripts/chat.py`
- `tests/test_chat_client.py`
- `tests/test_latency_optimizations.py`

## Step 3: Extend exact evidence tracing

Add to `EvidenceTrace`:

- validated `query_plan`;
- selected lane and reason codes;
- every executed subquery and retrieval round;
- deterministic tool/calculation results;
- re-rank decision and fallback reason;
- final selected/dropped evidence ids and context budget.

Trace only actions that actually occurred. A rejected planner attempt may be
represented as a reason code but its prompt/output must not be mixed into the
successful answer evidence.

**Files to modify:**
- `src/middleware/evidence_trace.py`
- `src/middleware/app.py`
- `eval/run_eval.py`
- `tests/test_eval_harness.py`

## Step 4: Run a three-configuration evaluation

Record in a future
`docs/plans/phase2.2/2.2.3-adaptive-rag-orchestration/RESULTS.md` only after
implementation:

1. legacy Phase 2.1 path;
2. adaptive lanes with deterministic tools disabled;
3. adaptive lanes plus deterministic tools and conditional re-ranking.

Use the repaired 2.2.1 evaluator and the conversational/compound set. Report:

- plan/router accuracy;
- Recall@10 and nDCG@10 overall and by lane;
- compound subquestion coverage;
- grounded faithfulness, policy compliance, and answer relevance;
- deterministic route accuracy and write-tool avoidance;
- p50/p95 total latency, TTFT, retrieval time, prompt characters/tokens;
- model, embedding, tool, retrieval-round, and reranker call counts;
- adaptive fallback and budget-exhaustion rates.

Do not use a live model while implementing offline behavior. The live comparison
is scheduled only when the user explicitly makes the GPU available.

**Files to modify:**
- `eval/run_eval.py`
- `eval/metrics.py`
- `eval/score.py`
- `eval/gate.py`
- `eval/README.md`

## Step 5: Define promotion and rollback

Promote adaptive mode only when:

- plan/router accuracy is at least 0.90;
- deterministic route accuracy is at least 0.95 with zero write-tool routes;
- complex-query correctness improves at least 10 percentage points;
- multi-turn Recall@10 improves at least 10 percentage points;
- single-turn nDCG@10 regresses by no more than 0.02;
- simple-query p95 latency regresses by no more than 10%;
- no request exceeds three subqueries, two retrieval rounds, one planning call,
  or one re-rank call;
- adaptive fallback is exercised successfully in fault-injection tests.

If any gate fails, keep `enable_adaptive_rag=false`, retain the results, and
fix or narrow the route before another evaluation. The legacy path remains the
rollback mechanism.

## Testing

Add offline integration tests:

- normal and streaming endpoints use equivalent adaptive context;
- feature-disabled response matches the legacy route;
- adaptive failure invokes legacy retrieval once;
- fast lane bypasses Chroma/planner/reranker;
- complex lane counters never exceed hard caps;
- deterministic tool results appear in final evidence and trace;
- metadata reports actual execution counts;
- evidence trace contains only the successful answer path;
- `/health` reports effective capabilities;
- old clients tolerate omitted orchestration metadata.

Use dependency injection and mocked clients. Do not start the model or network.

## Verification Checklist

- [ ] One feature switch selects a complete legacy or adaptive path
- [ ] `/query` and `/query/stream` share the same compiled context
- [ ] Adaptive failures fall back without losing the raw question
- [ ] Response and trace metadata report actual lane/budget behavior
- [ ] Legacy metadata and clients remain compatible
- [ ] Three evaluation configurations have an explicit future results format
- [ ] Promotion gates cover quality, latency, call counts, and safety
- [ ] Legacy mode remains a tested rollback
- [ ] All integration tests are offline and deterministic
