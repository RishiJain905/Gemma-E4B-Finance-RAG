# 2.2.3.3 — Adaptive Lanes, Context Budget & Conditional Re-Ranking

## Objective

Add a bounded orchestrator that selects a fast, standard, or complex lane from
the explicit query plan; enforces one shared execution budget; assembles only
useful context; and invokes the existing re-ranker only when it can plausibly
improve document selection.

## Why This Matters

Not every finance question deserves the same cost. Exact SQLite lookups should
not pay for embeddings and model-selected tools, while compound questions need
more than one narrow retrieval. Running every available stage on every request
would make the local model slower without reliably improving answers. Adaptive
lanes make cost explicit and keep complex behavior tightly bounded.

## Step 1: Create the bounded orchestrator

Create `src/middleware/adaptive_orchestrator.py` with:

- `Lane`: `fast|standard|complex`.
- `ExecutionBudget` with counters and hard limits:
  - at most **3 subqueries total**, including the original `sq0`;
  - at most **2 retrieval rounds total**;
  - at most **1 optional pre-answer planning model call**;
  - at most **1 re-ranking call**;
  - deterministic tool cap from 2.2.3.2.
- `OrchestrationResult`
  - selected lane and reason codes;
  - original `QueryPlan`;
  - deterministic tool/calculation results;
  - merged facts and documents;
  - subqueries executed and retrieval rounds used;
  - whether planning or re-ranking ran;
  - context size and any fail-soft fallback reason.

Every counter is incremented through `ExecutionBudget.consume(kind)`. Calling
code cannot bypass the limits. Budget exhaustion returns the best evidence
already collected and a partial reason; it never starts an unbounded loop.

**Files to create:** `src/middleware/adaptive_orchestrator.py`.

## Step 2: Select the cheapest sufficient lane

Use deterministic lane rules:

### Fast lane

Choose fast only when the deterministic router has a complete route and the
plan has no qualitative document obligation.

- Execute parameterized SQLite/read tools and whitelisted calculations.
- Return a deterministic answer when enabled and every obligation is covered.
- Otherwise pass compact structured evidence through one normal generation
  call.
- Do not run Chroma, BM25, re-ranking, query decomposition, or a planning call.

### Standard lane

Choose standard for one coherent topic that the existing hybrid retriever can
serve in one round:

- Run the existing `Retriever.retrieve()` with `sq0`.
- Include deterministic tool evidence when the router produced a safe partial
  route.
- Use current vector + BM25/RRF behavior.
- Do not make a planning call or decompose the query.

### Complex lane

Choose complex only when the plan has independently answerable obligations,
for example multiple intents, structured plus qualitative evidence, more than
two entities, or distinct entity/period clauses.

- Start from `sq0`; 2.2.4.2 may add at most two derived subqueries.
- Execute all subqueries for a round as one bounded set. A subquery does not
  count as a separate retrieval round.
- Allow a second retrieval round only through the corrective rule in 2.2.4.1.
- A pre-answer planning call is optional, disabled by default, and allowed only
  when deterministic parsing cannot assign retrieval modes. It must return
  strict JSON matching `QueryPlan`, pass validation, and consume the single
  planning-call budget. Invalid output is ignored in favor of the rule plan.

Lane selection must be observable and stable for identical inputs.

## Step 3: Apply one context budget

Add `ContextBudget` in `src/middleware/adaptive_orchestrator.py`. Measure
characters with an estimated-token field for telemetry; do not introduce a
tokenizer dependency.

Default lane caps:

- fast: 4,000 context characters;
- standard: 12,000 context characters;
- complex: 18,000 context characters;
- never exceed `adaptive_max_context_chars`, default 18,000.

Selection order:

1. Exact facts/tool results matching requested entity, metric, and period.
2. One best nonblank evidence item for each uncovered subquery/entity.
3. Remaining documents by retrieval/re-rank score.
4. Lower-authority, stale, duplicate, and redundant chunks last.

The budgeter must:

- Preserve `original_question` in full outside the evidence budget.
- Read document bodies through one canonical helper supporting
  `document|text|content`; blank bodies are discarded.
- Deduplicate documents by stable id and parent/chunk identity.
- Never cut a fact record midway or silently drop all evidence for a covered
  subquery.
- Emit dropped counts and reason codes.
- Prefer whole chunks; truncate an oversized final chunk only as a last resort
  and mark it `truncated=True`.

Modify `src/middleware/prompt_augmenter.py` to accept the selected evidence
instead of applying its independent unused truncation policy. Keep
`truncate_if_needed()` temporarily for compatibility, but the adaptive path
must have one budget owner.

**Files to modify:** `src/middleware/prompt_augmenter.py`.

## Step 4: Re-rank only when justified

Reuse `src/middleware/reranker.py`; do not add another ranking model.

Run one re-rank only when all are true:

- re-ranking and adaptive conditional re-ranking are enabled;
- the lane is standard or complex;
- candidate documents exceed final `top_k_documents`;
- document evidence is required;
- and at least one ambiguity signal exists:
  - vector and lexical top-three sets have low overlap;
  - multiple entities/subqueries compete for the same result slots;
  - top vector distances are tightly clustered;
  - or the query contains qualitative intent plus exact finance anchors.

Skip re-ranking for fast-lane requests, exact fact lookups, empty candidates,
or candidate counts already at/below the final limit. A re-ranker failure keeps
the RRF order and records `rerank_fallback`.

Expose a small `Retriever.retrieve_candidates()` seam if needed so the
orchestrator can decide before final truncation. Preserve
`Retriever.retrieve()` unchanged for feature-disabled callers.

**Files to modify:** `src/middleware/retriever.py`,
`src/middleware/reranker.py` only if a non-mutating score API is needed.

## Step 5: Add configuration and fail-soft behavior

Add to `src/middleware/config.py` and `configs/middleware.yaml`:

- `enable_adaptive_rag: bool = False`
- `adaptive_enable_planning_call: bool = False`
- `adaptive_max_subqueries: int = 3` (clamp 1–3)
- `adaptive_max_retrieval_rounds: int = 2` (clamp 1–2)
- `adaptive_max_planning_calls: int = 1` (clamp 0–1)
- `adaptive_max_context_chars: int = 18000`
- `adaptive_conditional_rerank: bool = True`

Reject invalid limits at configuration load by clamping to the safe maximum
and logging once. Environment overrides follow the existing config pattern.

If planning, routing, budgeting, or adaptive retrieval raises, log the stage
and use the existing single-query `Retriever.retrieve()` result. A query must
never fail because the adaptive layer failed.

**Files to modify:** `src/middleware/config.py`,
`configs/middleware.yaml`.

## Testing

Create `tests/test_adaptive_orchestrator.py`:

- `test_fast_lane_skips_chroma_reranker_and_planner`.
- `test_standard_lane_uses_existing_hybrid_once`.
- `test_complex_lane_caps_three_subqueries`.
- `test_retrieval_round_budget_stops_at_two`.
- `test_planning_call_budget_stops_at_one`.
- `test_invalid_planning_json_uses_rule_plan`.
- `test_context_budget_preserves_raw_question_and_required_coverage`.
- `test_blank_document_body_is_dropped`.
- `test_conditional_rerank_runs_on_channel_disagreement`.
- `test_rerank_skipped_for_exact_fact_lookup`.
- `test_reranker_failure_preserves_rrf_order`.
- `test_adaptive_failure_falls_back_to_existing_retriever`.
- `test_feature_disabled_path_is_byte-for-byte_compatible_metadata`.

Use fake retrievers, tool handlers, and planning clients. No model, middleware,
Chroma process, or network.

Latency gates, measured separately from final token generation:

- fast-lane median orchestration latency is at most 50% of the current
  tool-selection path;
- standard-lane p95 retrieval overhead regresses by no more than 10%;
- complex-lane orchestration p95 is no more than 2x standard retrieval or
  250 ms additional overhead, whichever limit is larger;
- simple-query re-rank invocation rate is 0%.

## Verification Checklist

- [ ] Fast, standard, and complex lanes have deterministic selection rules
- [ ] Central budget enforces max 3 subqueries, 2 retrieval rounds, 1 planning
      call, and 1 re-rank call
- [ ] Fast lane uses deterministic SQLite/tools/calculations
- [ ] Standard lane preserves the existing hybrid retrieval behavior
- [ ] Complex lane is bounded and planning is optional
- [ ] One context budget preserves raw question and required evidence coverage
- [ ] Blank/duplicate context is removed before generation
- [ ] Re-ranking runs only on documented ambiguity signals and fails soft
- [ ] Feature-disabled or failed adaptive execution uses the current path
- [ ] Offline lane and budget tests pass
- [ ] Measured latency stays within the per-lane gates
