# 2.2.3.1 — Multi-Entity Intent & Query Plans

## Objective

Replace the current single-ticker, single-intent parse result with an explicit
query-plan contract that preserves the user's raw question and represents every
resolved entity, intent, metric, and period needed to answer it. Keep the
existing `IntentParser.parse()` result available as a compatibility view so
this can ship behind a feature flag without changing the current query path.

## Why This Matters

The current parser chooses one ticker and the first matching intent. A request
such as "Compare NVDA and AMD revenue trends, then summarize their risks" loses
part of its meaning before retrieval starts. Longer prompts therefore perform
worse than short single-purpose prompts even though the model has enough
context capacity. An explicit, bounded plan gives retrieval and tools a stable
contract without asking the model to infer routing on every request.

## Step 1: Define the query-plan contract

Create `src/middleware/query_plan.py` with small dataclasses or typed models:

- `QueryEntity`
  - `ticker: str`
  - `resolved_name: str | None`
  - `confidence: float`
  - `source: str`
  - `mention: str` and `start: int` so mention order is deterministic.
- `QuerySubquery`
  - `id: str` using stable request-local ids (`sq0`, `sq1`, ...).
  - `text: str`
  - `entity_tickers: tuple[str, ...]`
  - `intents: tuple[str, ...]`
  - `metrics: tuple[str, ...]`
  - `periods: tuple[str, ...]`
  - `retrieval_modes: tuple[str, ...]` drawn from
    `facts|documents|macro|tools`.
  - `derived: bool` and `parent_id: str | None`.
- `QueryPlan`
  - `original_question: str` — the exact request text; never normalized,
    rewritten, truncated, or replaced.
  - `retrieval_query: str` — the validated standalone query compiled by
    2.2.2, or the raw question when no conversation rewrite is needed.
  - `normalized_question: str` — optional matching-only representation.
  - ordered `entities`, `intents`, `metrics`, and `periods`.
  - `subqueries`, initially containing only `sq0` with `retrieval_query`.
  - `primary_intent` for legacy strategy selection.
  - `reason_codes` for observable rule matches.

Enforce these invariants in one `QueryPlan.validate()` helper:

- `original_question` is nonblank and unchanged from the request.
- `retrieval_query` is nonblank, separate from `original_question`, and may
  contain only validated current/history slots.
- Entity tickers are uppercase and deduplicated in first-mention order.
- Intent, metric, and period lists are deduplicated without sorting away user
  order.
- A plan has one to three subqueries total; `sq0` is always the validated
  standalone retrieval query.
- Derived subqueries may narrow the plan but may not introduce an entity,
  metric, or period that was not present in the plan.

**Files to create:** `src/middleware/query_plan.py`.

## Step 2: Resolve all explicit entities

Extend `src/middleware/symbol_resolver.py` with
`resolve_all(text) -> list[Resolution]`:

- Collect exact company names, catalog aliases, and uppercase symbols with
  their text spans.
- Sort by mention position, prefer the longest overlapping alias, and
  deduplicate by ticker.
- Preserve the existing ambiguity guards for ordinary words such as "target"
  and "gap".
- Use fuzzy resolution only when no exact entity was found for the candidate
  mention. Never fuzzy-match every token in a long question.
- Keep `resolve()` unchanged by returning the first `resolve_all()` result
  or `NO_MATCH`.

Ticker override behavior must be explicit:

- Add the override first with `source="override"`.
- Keep other explicitly mentioned tickers for comparisons.
- If the question contains no other entity, the override is the only entity.

**Files to modify:** `src/middleware/symbol_resolver.py`.

## Step 3: Extract multiple intents, metrics, and periods

Add `IntentParser.parse_plan(question, retrieval_query=None,
override_ticker=None)` in
`src/middleware/intent_parser.py`:

- Preserve `question` as `original_question`; run entity/intent/metric/period
  matching on `retrieval_query or question`.
- Run every intent pattern and retain every matched intent in priority order.
- Use `general` only when no specific intent matched.
- Continue extracting every unique metric.
- Extract every explicit quarter/year/range instead of returning only the first
  timeframe.
- Set `primary_intent` using the existing priority table solely for backward
  compatibility.
- Populate only baseline `sq0` from the validated retrieval query; selective
  decomposition belongs to 2.2.4.2.

Add `QueryPlan.to_legacy_intent()` so feature-disabled callers still receive
the current dictionary keys: `ticker`, `metrics`, `question_type`,
`timeframe`, `original_question`, and ticker-resolution metadata. The
adapter uses the first ordered entity and primary intent; it must not mutate
the full plan.

**Files to modify:** `src/middleware/intent_parser.py`.

## Step 4: Keep the raw question on every downstream boundary

Document and enforce the query-text contract:

- Matching and classification may use `normalized_question`.
- Embedding and lexical retrieval use `retrieval_query`/subquery text.
- Prompt display and answer generation preserve `original_question`; telemetry
  records separate digests for raw and retrieval forms.
- Any later standalone-query rewrite is stored separately and never overwrites
  the raw input.
- A rejected plan returns a structured reason and falls back to the existing
  `IntentParser.parse()` path; it never fails the user request.

Do not integrate the plan into `/query` yet; 2.2.3.4 owns the request-path
switch and response metadata.

## Testing

Create `tests/test_query_plan.py` and extend
`tests/test_intent_parser.py`:

- `test_raw_question_preserved_exactly` — whitespace and punctuation survive
  in `original_question`.
- `test_retrieval_query_is_separate_and_becomes_sq0` — carried context can
  enrich retrieval without changing the raw question.
- `test_resolve_all_preserves_mention_order` — "AMD versus NVIDIA" returns
  `AMD, NVDA`, not map order.
- `test_override_keeps_comparison_entity` — an override plus another explicit
  ticker produces two entities.
- `test_multi_intent_plan` — revenue trend plus risks retains
  `trend|risk`.
- `test_multiple_periods_retained` — 2023 through 2025 is not collapsed to one
  year.
- `test_ambiguous_words_do_not_become_tickers`.
- `test_plan_rejects_derived_entity_drift`.
- `test_legacy_adapter_matches_existing_parse_contract`.

All tests use in-memory resolver catalogs or stubs. No network, Chroma,
middleware, or model is allowed.

Quality gate: entity, intent, metric, and period micro-F1 must be at least
0.90 on a checked-in compound-query fixture set, with zero raw-question
mutation cases.

## Verification Checklist

- [ ] `QueryPlan`, `QueryEntity`, and `QuerySubquery` have explicit,

- [ ] Raw user question is preserved exactly and remains baseline `sq0`

- [ ] Legacy intent adapter preserves the current parser API
- [ ] Parser/resolver failures fall back to the existing path
- [ ] Offline parser fixture micro-F1 is at least 0.90
- [ ] `tests/test_query_plan.py` and extended intent tests pass offline
