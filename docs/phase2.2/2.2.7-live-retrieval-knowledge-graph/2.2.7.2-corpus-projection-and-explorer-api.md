# 2.2.7.2 — Corpus Projection & Explorer API

## Objective

Project the existing Store into a read-only, paginated exploration graph so the
localhost UI can browse sources, tickers, metrics, filings, sections, documents,
and freshness without introducing a graph database or loading the entire corpus
into the browser.

## Why This Matters

The live trace answers “what did this query use?” The user also needs to inspect
“what information does my RAG contain?” A corpus explorer should reveal stored
coverage and provenance, but duplicating SQLite/Chroma into Neo4j or an
LLM-derived GraphRAG index would add synchronization and staleness problems.
The Store is authoritative; graph nodes can be projected on demand.

## Step 1: Define deterministic corpus node types

Create `src/middleware/corpus_graph.py` with stable opaque ids and projections:

- `source` — Yahoo, SEC CompanyFacts/filings, FRED, GDELT, transcripts, IR,
  estimates;
- `ticker` — resolved symbol and company name when known;
- `metric` — canonical metric/concept and supported units;
- `fact` — bounded latest/as-of observation metadata;
- `filing` — accession, form, dates, processing/index status;
- `section` — filing parent section and child count;
- `document_family` — non-SEC parent id/source/ticker/date/chunk count;
- `freshness` — source/ticker status and next update;
- `scheduler_source` — cadence and last run.

Relations include `contains`, `describes`, `reported_by`, `filed_as`,
`has_section`, `has_chunk_family`, `freshness_for`, and `scheduled_by`.

Node ids must not expose local file paths. Use durable source identifiers or a
URL-safe hash of the canonical Store key.

**Files to create:**
- `src/middleware/corpus_graph.py`
- `tests/test_corpus_graph.py`

## Step 2: Add bounded Store inventory seams

Add read-only methods only where existing facades cannot provide the data:

- source/ticker counts and freshness summaries;
- metric/concept search with ticker/unit filters;
- filing list and section-family counts;
- document family search by source/ticker/date;
- bounded neighbor/detail reads.

Every method accepts `limit`, cursor/offset, and filters with safe maxima. Use
parameterized SQLite queries and Chroma metadata filters. Never fetch an
external source, refresh data, embed text, or call the model from explorer
methods.

Do not expose arbitrary SQL, Chroma `where` JSON, filesystem paths, or raw
collection dumps through the API.

- `src/storage/chroma_store.py`

## Step 3: Expose overview, search, and expansion endpoints

Add to `src/middleware/graph_api.py`:

- `GET /graph/api/corpus/overview` — source groups, counts, freshness, corpus
  revision;
- `GET /graph/api/corpus/search?q=&kinds=&sources=&ticker=&limit=` — matching
  nodes only;
- `GET /graph/api/corpus/nodes/{node_id}` — bounded detail;
- `GET /graph/api/corpus/nodes/{node_id}/neighbors?cursor=&limit=&relations=` —
  one expansion page;
- `GET /graph/api/corpus/filings/{accession}/sections?cursor=&limit=`;
- `GET /graph/api/corpus/refresh-status` — read freshness/scheduler state only.

Responses contain `nodes`, `edges`, `next_cursor`, `truncated`, and
`corpus_revision`. Reject invalid/expired opaque ids and limits above the cap.

No endpoint mutates data. Refresh remains the existing separately guarded API
and is not linked to a graph click.

**Files to modify:**
- `src/middleware/graph_api.py`
- `src/middleware/models.py`
- `tests/test_graph_api.py`

## Step 4: Limit body/detail exposure

Overview/search results contain labels and metadata only. A detail request may
return:

- up to 1,000 characters of a document/section excerpt;
- one fact value with unit, period, as-of, source, and conflict metadata;
- source URL when stored and valid HTTP(S);
- freshness/status/error summary with secrets and local paths removed.

Full raw document or filing bodies are outside this API. The explorer links
source URLs but does not fetch or proxy them.

## Step 5: Add scale and consistency behavior

- Cache only the overview for a short TTL keyed by `Store.retrieval_revision()`.
- Search/neighbor pages read the current revision and return it.
- If the revision changes while expanding, the UI shows “corpus updated” and
  offers reload; it does not merge incompatible pages silently.
- Default visible graph target is under 500 nodes; hard client/server page caps
  prevent more than 2,000 elements in one expansion response.
- No corpus endpoint performs an O(all documents) body read during a normal
  overview.

## Testing

Use seeded SQLite and fake Chroma metadata. Cover source overview, search
filters, opaque ids, parameterized queries, pagination/cursors, section
neighbors, revision changes, excerpt/path/secret redaction, invalid limits, and
proof that no embedding/model/network/write method is invoked.

Performance gates on the seeded representative corpus:

- overview p95 below 100 ms after warm Store initialization;
- search/neighbor page p95 below 200 ms;
- response element/body limits always enforced.
