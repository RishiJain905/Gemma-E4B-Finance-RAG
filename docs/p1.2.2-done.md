- **Connection settings:**
  - `PRAGMA journal_mode=WAL` — enables concurrent reads during writes
  - `PRAGMA foreign_keys=ON` — enforces referential integrity
  - `row_factory = sqlite3.Row` — dict-like row access

  - `cache_meta` — tracks per-ticker data freshness per source

## CRUD Methods Delivered

**Fundamentals:**
- `upsert_fundamental(...)` — Insert or update a single financial metric
- `get_fundamental(ticker, metric, period=None)` — Get latest value for a ticker+metric, optionally filtered by period
- `get_fundamentals_batch(ticker, metrics=None)` — Get multiple metrics for a ticker at once, returning `{metric: value}`

**Filing Tracking:**
- `register_filing(...)` — Register a filing as unprocessed; returns `True` if new
- `mark_filing_parsed(accession, embedding_id=None)` — Mark a filing as successfully parsed
- `get_unprocessed_filings(limit=10)` — Retrieve filings with `status='unprocessed'`

**Cache Management:**
- `get_cache_status(ticker, source)` — Return cache metadata row or `None`
- `mark_cache_fresh(ticker, source, ttl_hours=24)` — Update cache metadata after successful ingestion
- `mark_cache_stale(ticker, source, error=None)` — Mark cache as stale with optional error message
- `get_stale_cache_entries(limit=20)` — Find entries past their scheduled update time

**Ingestion Logging:**
- `log_ingestion_start()` — Start a new ingestion run and return `run_id`
- `log_ingestion_complete(run_id, status, items, new, updated)` — Finalize run and compute `duration_seconds`

**Middleware Query Support:**
- `search_facts(ticker=None, metric=None, source=None, limit=10)` — Flexible fact search with optional filters

## Execution Workflow Notes

- **Initialization is self-contained:** `SQLiteStore.__init__` automatically creates the `data/` directory if missing and applies the schema via `executescript`. No manual `sqlite3` CLI steps are required.
- **WAL mode compatibility:** WAL requires a local filesystem. If `data/` resides on a network drive, switch to `DELETE` journal mode or relocate `data/` locally.
- **Schema evolution strategy:** For this phase, schema changes require deleting `data/finance.db` and re-initializing. Future iterations may introduce Alembic-style migrations if the schema stabilizes.
- **Concurrency:** WAL mode allows readers to proceed while a writer holds the lock. This supports the planned daily ingestion cron without blocking the FastAPI middleware queries.
