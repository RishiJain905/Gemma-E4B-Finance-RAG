# 1.1.6 — Document Model Parameters

## Objective

Record the exact configuration and capabilities of the TraceAlchemy model as served by `llama-server` on your Windows + AMD RDNA3 setup. This creates a reference document that the middleware (Phase 1.5) and future components use to configure their requests correctly.

## Why This Matters

The middleware doesn't know anything about the model's capabilities by default — it needs to be told:

- What endpoint to hit (port 8087 on Windows)
- What context size is available (131072 tokens)
- MTP speculative decoding details
- AMD-specific cache quantization settings
- Embedding dimension

Without this documented, the middleware developer has to guess. With it documented in `configs/model.yaml`, every component aligns.

## Per-Task Parameters

Different tasks need different model behavior — recorded in the config:

| Task | Temperature | Max Tokens | Why |
|------|-------------|------------|-----|
| **Fact Extraction** (SEC filings) | 0.1 | 1024 | Low temp = deterministic, consistent parsing. No creativity for financial data. |
| **General Q&A** (with RAG) | 0.7 | 512 | Balanced — grounded by retrieved context but natural language. |
| **Deep Analysis** | 0.5 | 2048 | Analytical with some room for synthesis, but tight enough to avoid speculation. |

## What to Confirm After Running

Once you've run the server and done health checks (Task 1.1.4), update the runtime section at the bottom of `configs/model.yaml`:

```yaml
# Add to configs/model.yaml after testing
runtime:
  tokens_per_second: 30         # Measured during MTP decoding
  mtp_acceptance_rate: 0.85     # Fraction of draft tokens accepted by main model
  gpu_memory_usage_gb: 12       # VRAM used at 128K context + Q8_0
  stable_context_tested: 131072 # Confirmed working
```

You can find the MTP acceptance rate in the server logs — look for lines like:
```
mtp: accepted 3/3 tokens (draft block accepted)
mtp: accepted 2/3 tokens (1 rejected, fallback)
```
