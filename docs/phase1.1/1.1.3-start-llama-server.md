# 1.1.3 — Start llama-server with Optimal Configuration

## Objective

Launch `llama-server` on your Windows machine with parameters tuned specifically for the TraceAlchemy Q8_0 model on an AMD RDNA3 GPU, including MTP speculative decoding for faster inference.

## Environment

| Component | Value |
|-----------|-------|
| OS | Windows |
| GPU | AMD RDNA3 (gfx1101) |
| Build | `atomic-llama-cpp-turboquant\build-rdna3-gfx1101` |
| Main Model | `gemma-4-E4B-it.Q8_0.gguf` (~9.6 GB) |
| Draft Model | `gemma-4-E4B-it-assistant.F16.gguf` (MTP head) |
| Context | 131,072 tokens (full 128K + overhead) |

## Why This Matters

Your setup is different from a standard llama.cpp deployment in several important ways:

1. **AMD RDNA3** — uses the ROCm/HIP backend via the `build-rdna3-gfx1101` custom build, not CUDA or Metal
2. **Q8_0 quantization** — higher precision than Q4 (better quality, larger memory footprint)
3. **Full 128K context** — the model supports up to 128K tokens natively, and you're using all of it
4. **MTP speculative decoding** — a draft model predicts tokens ahead, making inference ~2-3x faster without quality loss
5. **Cache quantization** — `q8_0` for key cache, `turbo4` for value cache — AMD-specific optimizations for memory bandwidth

## The Command

```powershell
# Run from PowerShell in the build directory
cd F:\Personal\TQ-Optimizer-Test\atomic-llama-cpp-turboquant

.\build-rdna3-gfx1101\bin\llama-server.exe `
  -m "D:\LOCAL-MODELS\trjxter\TraceAlchemy-Gemma-4-E4B-Finance-IT-gguf\gemma-4-E4B-it.Q8_0.gguf" `
  --mtp-head "D:\LOCAL-MODELS\AtomicChat\gemma-4-E4B-it-assistant-GGUF\gemma-4-E4B-it-assistant.F16.gguf" `
  --spec-type mtp `
  --draft-block-size 3 `
  --host 127.0.0.1 --port 8087 `
  -c 131072 -ngl 99 -np 1 -fa on `
  -ctk q8_0 -ctv turbo4 `
  -t 8 `
  --embeddings `
  --pooling mean
```

## Parameter Breakdown

### Model & Draft Model

| Flag | Value | Why |
|------|-------|-----|
| `-m` | `gemma-4-E4B-it.Q8_0.gguf` | The actual TraceAlchemy finetune in Q8_0 precision |
| `--mtp-head` | `gemma-4-E4B-it-assistant.F16.gguf` | **MTP draft model** — a small assistant model that predicts the next 3 tokens |
| `--spec-type` | `mtp` | Enables **Multi-Token Prediction** speculative decoding |
| `--draft-block-size` | `3` | Draft model predicts 3 tokens ahead per step |

**How MTP Speculative Decoding Works:**

```
Normal decoding:
  "NVIDIA" → [model predicts] → "reported" → [model predicts] → "record" → ...

MTP decoding (spec_type=mtp, draft_block_size=3):
  "NVIDIA" → [draft predicts 3 tokens] → "reported record revenue"
           → [main model verifies all 3 at once] → ✅ accepted → 3x faster
```

The draft model is smaller and faster but accurate enough that most of its predictions are accepted by the main model. This effectively gives you 2-3x throughput on the same hardware.

### Server & Network

| Flag | Value | Why |
|------|-------|-----|
| `--host` | `127.0.0.1` | Localhost only — no network exposure |
| `--port` | `8087` | Using 8087 instead of default 8080. The middleware (Phase 1.5) will connect to `http://127.0.0.1:8087` |

### Context & GPU

| Flag | Value | Why |
|------|-------|-----|
| `-c` | `131072` | **Full 128K context** + 3K headroom. The model natively supports 128K and your 16GB VRAM handles the Q8_0 quant at this length. This is a major advantage over smaller setups — you can pass entire SEC filings in one shot. |
| `-ngl` | `99` | Offload all layers to GPU. AMD RDNA3 with ROCm handles the full model. |
| `-np` | `1` | Single user, one parallel request. |
| `-fa` | `on` | **Flash attention** — critical for 128K context. Without this, attention memory would be O(n²) and OOM instantly. |

### Cache & Memory Optimization

| Flag | Value | Why |
|------|-------|-----|
| `-ctk` | `q8_0` | **Key cache in Q8_0** — 8-bit quantization of the key-value attention cache. Saves VRAM while maintaining quality. |
| `-ctv` | `turbo4` | **Value cache in turbo4** — an AMD/ROCm-specific 4-bit format for the value cache. Further VRAM savings. |
| `-t` | `8` | **8 CPU threads** for non-GPU tasks (prompt processing prep, etc.). Match your CPU core count for AMD Ryzen. |

### Embedding Support

| Flag | Why |
|------|-----|
| `--embeddings` | Enables the `/v1/embeddings` endpoint. Required by ChromaDB in Phase 1.2. Without this flag, embedding requests return a 404. |
| `--pooling mean` | Use **mean pooling** to generate a single embedding vector for the entire input sequence. Without this, the embedding endpoint may return per-token embeddings instead of a single document-level vector, which ChromaDB cannot consume. **Mean pooling** averages all token embeddings into one — this is the standard for document-level semantic search.

> **What happens without `--pooling mean`?** llama-server defaults to no pooling, which returns embeddings per-token (one vector per token in the input). ChromaDB expects one vector per document. With `--pooling mean`, the server averages all token vectors into a single document embedding — exactly what ChromaDB needs.

## What Could Go Wrong

| Problem | Likely Cause | Fix |
|---------|-------------|------|
| `llama-server.exe not found` | Wrong path or build dir | Verify the path: `Get-ChildItem $BuildDir\bin\llama-server.exe` |
| `ROCm error` / `hipError` | AMD driver issues | Update Radeon drivers to the latest (Adrenalin 24.x+). Ensure ROCm libraries are in PATH. |
| `cannot load model` | Model path wrong or file corrupt | Double-check the path. Verify GGUF magic bytes (Task 1.1.2). |
| Port 8087 in use | Another process on that port | Check with `netstat -aon \| findstr :8087`. Kill the process or use a different port. |
| OOM on startup | 128K context + Q8_0 exceeds VRAM | Drop context: `-c 65536` instead. Or reduce to Q4_K_M quant if available. |
| MTP head not found | Draft model path is wrong | Verify the F16 GGUF exists at the specified path. |
| Slow even with MTP | Draft model not actually accelerating | Check server logs for "accepted/rejected" ratio. If rejection rate > 50%, lower `--draft-block-size` to 2. |
| `--embeddings` flag missing | Endpoint returns 404 on embed requests | Restart with `--embeddings` flag |

## Running in Background (Windows)

Unlike Linux, `nohup` doesn't exist on Windows. Use the PowerShell wrapper script instead:

```powershell
# From the project root
.\scripts\serve_model.ps1 start
```

This runs the server as a background process with logging. See Task 1.1.5 for the full wrapper.
